# 만성질환 생활습관 챌린지 UI/UX 구현 가이드

| 항목 | 내용 |
|---|---|
| 문서 목적 | Codex와 개발자가 화면을 만들거나 수정할 때 따를 공통 UI/UX 기준 정의 |
| 적용 범위 | `src/frontend`의 사용자용 웹 화면과 신규 프런트엔드 화면 |
| 주요 사용자 | 만 45세 이상 당뇨병 미진단자, 디지털 서비스 사용이 익숙하지 않은 사용자 |
| 문서 버전 | v1.0 |
| 작성일 | 2026-09-07 |

> 이 문서는 시각적 참고자료가 아니라 구현 지침이다. Codex는 프런트엔드 화면을 생성·수정·검토할 때 이 문서를 먼저 확인한다.

## 1. 문서 우선순위

서로 다른 문서의 내용이 충돌하면 다음 순서를 따른다.

1. `AGENTS.md`의 의료·AI 안전 및 저장소 규칙
2. `docs/SERVICE_SCOPE_AND_SAFETY_COPY.md`의 대상·제외 조건과 확정 문구
3. `docs/REQUIREMENTS.md`, `docs/API_SPEC.md`의 기능·데이터 계약
4. 이 문서의 UI/UX 배치와 표현 기준
5. 토스·원티드 등 외부 서비스의 시각적 참고

Codex는 UI를 보기 좋게 만들기 위해 의료 안전 문구, 적합성 분기, 개인정보 최소수집, API 필드 의미를 임의로 바꾸면 안 된다.

## 2. 핵심 설계 원칙

### 2-1. 한 화면에는 하나의 주된 목적을 둔다

- 화면에 들어온 사용자가 해야 할 가장 중요한 행동을 하나로 정한다.
- 가장 중요한 행동만 채워진 주 버튼으로 표현한다.
- 부가 기능은 보조 버튼, 텍스트 링크 또는 다음 화면으로 분리한다.
- 사용자가 지금 무엇을 해야 하는지 제목과 첫 문단만 읽어도 이해할 수 있어야 한다.

### 2-2. 사용자가 다음 행동을 예측할 수 있게 한다

- 버튼은 결과가 드러나는 동사형 문구를 사용한다.
  - 권장: `건강정보 저장`, `결과 확인`, `4주 챌린지 시작`
  - 지양: `확인`, `진행`, `다음`만 단독 사용
- 링크, 버튼, 카드가 같은 행동을 하면 같은 이름을 사용한다.
- 클릭이나 제출 전에 일어날 결과를 갑자기 바꾸지 않는다.
- 새 창, 자동 이동, 자동 제출은 꼭 필요한 경우가 아니면 사용하지 않는다.

### 2-3. 건강 서비스는 불안을 키우지 않는다

- 위험 결과는 진단처럼 단정하지 않는다.
- 사용자를 평가하거나 실패를 비난하는 문구를 사용하지 않는다.
  - 권장: `오늘부터 다시 이어갈 수 있어요.`
  - 지양: `또 실패했어요.`
- 위험도가 높거나 경고 증상이 있으면 챌린지보다 검사·의료기관 안내를 먼저 보여준다.
- 낮은 위험도에도 위험이 전혀 없다는 의미가 아님을 함께 안내한다.
- 생활습관 기록의 증감을 치료 효과나 질병 개선율로 표현하지 않는다.

### 2-4. 토스와 원티드는 원칙만 참고한다

- 토스에서 참고할 점: 쉬운 문장, 충분한 여백, 한 번에 하나의 핵심 행동, 명확한 상태 피드백
- 원티드에서 참고할 점: 익숙한 상단 내비게이션, 탐색하기 쉬운 정보 묶음, 목록·검색·필터 구조
- 두 서비스의 색상, 애니메이션, 카드 모양, 화면 밀도를 그대로 복제하지 않는다.
- 본 서비스의 고령 사용자, 건강정보 입력, 의료 안전 요구를 우선한다.

## 3. 전체 정보 구조

### 3-1. 비로그인 데스크톱 헤더

```text
[간당간당 로고]  서비스 소개  이용 방법  건강정보 안내        로그인  회원가입
```

- 로고는 왼쪽 상단에 배치하고 클릭하면 첫 화면으로 이동한다.
- 주요 정보 메뉴는 로고 오른쪽 또는 헤더 중앙에 배치한다.
- `로그인`과 `회원가입`은 오른쪽 상단에 배치한다.
- 두 버튼을 모두 강한 주 버튼으로 만들지 않는다.
  - 기본값: 로그인은 텍스트 또는 보조 버튼, 회원가입은 주 버튼
- 현재 프로토타입처럼 가입 흐름 자체가 핵심 데모인 경우 `시작하기` 하나로 통합할 수 있다.

### 3-2. 로그인 후 데스크톱 헤더

```text
[간당간당 로고]  홈  챌린지  건강 기록  리포트  함께하기        [프로필]
```

- 로그인·회원가입 자리는 프로필 또는 `마이` 메뉴로 교체한다.
- 자주 쓰는 사용자 메뉴는 5~7개 이하로 유지한다.
- 현재 메뉴는 색상과 배경 또는 밑줄로 명확히 구분한다.
- 건강정보 수정, 동의 관리, 로그아웃은 프로필 메뉴 아래에 둔다.

### 3-3. 모바일 내비게이션

```text
상단: [뒤로]  화면 제목                              [도움/프로필]
하단: 홈 | 챌린지 | 기록하기 | 리포트 | 마이
```

- 인증 전에는 상단 메뉴 버튼 안에 로그인·회원가입을 배치할 수 있다.
- 인증 후 핵심 기능은 하단 탭 3~5개로 제공한다.
- `기록하기`처럼 가장 자주 수행하는 행동은 하단에서 쉽게 찾을 수 있어야 한다.
- 모바일에 데스크톱 메뉴를 축소해 억지로 모두 표시하지 않는다.

## 4. 화면별 구현 기준

### 4-1. 서비스 안내

화면에 다음 순서로 정보를 제공한다.

1. 서비스가 제공하는 가치
2. 진단·처방 서비스가 아니라는 짧은 안내
3. `위험 확인 → 생활습관 선택 → 4주 기록` 과정
4. 주 버튼 `시작하기`
5. 로그인한 기존 사용자를 위한 `로그인` 또는 `이어하기`

- 첫 화면의 큰 캐릭터는 1개를 원칙으로 한다.
- 캐릭터가 제목, 설명 또는 의료 안전 문구를 대신하면 안 된다.
- 긴 기능 목록보다 사용자가 얻는 결과와 예상 소요 과정을 먼저 보여준다.

### 4-2. 회원가입·로그인·동의

- 인증 화면은 중앙의 읽기 쉬운 단일 열로 구성한다.
- 입력 순서는 `이메일 → 비밀번호 → 제출 버튼`처럼 자연스럽게 유지한다.
- 입력 이름은 placeholder가 아니라 화면에 계속 보이는 `<label>`로 제공한다.
- 비밀번호에는 표시·숨기기 기능과 조건 안내를 제공한다.
- 오류는 해당 입력 바로 아래에 원인과 수정 방법을 표시한다.
- 사용자가 입력한 올바른 값은 오류 발생 후에도 유지한다.
- 개인정보 동의 화면은 수집 항목, 목적, 보유기간, 철회 방법을 확인할 수 있어야 한다.
- 서비스 계약 처리 정보와 별도 동의가 필요한 선택 정보를 구분한다.
- 선택 동의를 거부해도 핵심 서비스를 부당하게 막지 않는다.
- 건강정보·민감정보 동의는 일반 이용약관과 시각적으로 구분한다.

### 4-3. 적합성·안전 확인

- 한 화면에 질문을 너무 많이 넣지 않는다.
- 한 질문 안의 선택지는 라디오 버튼 또는 큰 선택 카드로 제공한다.
- `예/아니요`만 표시하지 말고 질문의 맥락이 화면에 남아 있게 한다.
- 현재 단계와 남은 단계를 보여준다.
- 부적합 또는 안전 분기가 발생하면 이유와 가능한 다음 행동을 함께 제공한다.
- 기진단자, 경고 증상, 모델 적용 범위 밖 사용자를 단순 오류 화면으로 보내지 않는다.
- 응급·경고 안내는 색상뿐 아니라 아이콘, 제목, 설명 문장으로 중복 표현한다.

### 4-4. 건강정보 입력

입력 항목은 다음 구조를 사용한다.

```text
[항목 이름] [필수/선택]
[사용자가 값을 어디서 확인할 수 있는지 설명]
[입력 필드] [단위]
[허용 범위 또는 오류 문구]
```

- 관련 항목을 기본정보, 건강검진, 생활습관 등 의미 단위로 묶는다.
- 필수·선택 여부와 단위를 입력 전에 보여준다.
- 숫자 입력은 현실적인 범위와 API 허용 범위를 동일하게 검증한다.
- 오류 시 값 전체를 초기화하지 않는다.
- 제출 시 첫 번째 오류로 초점을 이동하고 상단에도 오류 개수를 요약한다.
- 저장 전 검토 단계가 있다면 입력값과 단위를 함께 보여준다.
- 이전 단계에서 받은 정보를 다시 입력하게 하지 않는다.
- 입력 중 페이지를 벗어날 때 내용이 사라진다면 확인 절차를 제공한다.

### 4-5. 분석 대기·위험 결과

- 분석 대기 화면에는 현재 상태와 다음에 나타날 결과를 알려준다.
- 진행률을 실제로 계산할 수 없다면 가짜 백분율을 표시하지 않는다.
- 오래 걸리거나 실패했을 때 재시도와 이전 입력 보존 여부를 안내한다.
- 결과 화면의 정보 우선순위는 다음과 같다.

1. `진단이 아닌 위험 선별 결과`라는 설명
2. 위험 범주 `낮음·주의·높음`
3. 범주의 의미
4. 사용자가 취할 다음 행동
5. 위험·보호 요인
6. 모델·근거·한계에 대한 세부 정보

- 위험 범주는 색상만으로 구분하지 않는다.
- 승인되지 않은 원시 확률을 개인 발병확률처럼 표시하지 않는다.
- `높음`에서는 의료기관·검사 안내를 주 버튼으로 제공한다.
- 결과 세부정보는 접을 수 있지만 핵심 안전 문구는 접힌 영역에 숨기지 않는다.

### 4-6. 챌린지 선택·기록

- 사용자가 최대 3개를 선택할 수 있다는 규칙을 선택 전에 보여준다.
- 현재 선택 개수를 `2/3 선택`처럼 계속 표시한다.
- 챌린지 카드에는 행동, 빈도, 난이도, 안전 유의사항을 구분해 제공한다.
- 선택 상태를 테두리·체크 표시·배경으로 중복 표현한다.
- 선택 불가능한 이유가 있다면 비활성화만 하지 말고 이유를 알려준다.
- 기록 버튼은 오늘 수행 여부를 빠르게 저장할 수 있게 한다.
- 저장 직후 상태 변화와 성공 메시지를 제공한다.
- 미실천 기록은 실패 판정이 아니라 원인 확인과 목표 조정으로 연결한다.
- 연속 기록을 과도한 압박이나 처벌 방식으로 사용하지 않는다.

### 4-7. 대시보드

대시보드 첫 화면의 우선순위는 다음과 같다.

1. 오늘 할 일
2. 현재 챌린지 상태
3. 최근 7일 수행 요약
4. 건강정보·위험 결과 이력
5. 교육·함께하기 등 보조 기능

- 가장 위에는 `오늘의 챌린지 기록` 같은 즉시 행동을 둔다.
- 사용자가 이해하기 어려운 지표를 한꺼번에 나열하지 않는다.
- 그래프에는 제목, 단위, 기간, 텍스트 요약을 제공한다.
- 수행률과 질병 위험 변화를 인과관계처럼 연결하지 않는다.
- 데이터가 없을 때 빈 공간 대신 다음 행동을 안내한다.
  - 예: `아직 기록이 없어요. 오늘의 챌린지를 기록해 보세요.`
- 최신 기록과 과거 기록을 명확히 구분한다.

## 5. 공통 컴포넌트 규칙

### 5-1. 버튼 위계

| 종류 | 사용 목적 | 기본 표현 |
|---|---|---|
| 주 버튼 | 화면의 가장 중요한 다음 행동 | 브랜드 색상 채움 |
| 보조 버튼 | 이전, 취소, 대안 행동 | 흰 배경과 테두리 |
| 텍스트 버튼 | 세부보기, 도움말 등 낮은 우선순위 | 배경 없는 텍스트 |
| 위험 버튼 | 삭제, 탈퇴, 연결 해제 | 위험 색상과 확인 단계 |

- 같은 화면에서 주 버튼을 여러 개 경쟁시키지 않는다.
- 비활성화 상태만으로 필수 입력 오류를 설명하지 않는다.
- 삭제·탈퇴 버튼은 일반 저장 버튼과 떨어뜨려 배치한다.

### 5-2. 모달·팝업

- 짧은 확인, 간단한 입력, 중요한 경고에만 사용한다.
- 제목만으로 목적을 알 수 있어야 한다.
- 닫기 버튼은 오른쪽 상단에 배치하고 접근 가능한 이름을 제공한다.
- `Esc` 키와 명시적인 취소 버튼으로 닫을 수 있게 한다.
- 모달이 열리면 초점을 모달 안으로 이동하고 닫은 뒤 원래 위치로 돌려놓는다.
- 작성 중인 정보가 사라지는 경우 바깥 영역 클릭만으로 닫히지 않게 한다.
- 삭제 확인에는 삭제 대상을 구체적으로 표시한다.

### 5-3. 메시지와 상태

모든 비동기 기능은 최소한 다음 상태를 설계한다.

- 초기 상태
- 불러오는 중
- 성공
- 입력 오류
- 서버 오류
- 인터넷 연결 오류
- 권한 없음
- 데이터 없음
- 검색 결과 없음
- 재시도
- 세션 만료

메시지는 `문제 → 원인 → 다음 행동` 순서로 쓴다.

```text
기록을 저장하지 못했어요.
인터넷 연결을 확인한 뒤 다시 시도해 주세요.
[다시 저장]
```

### 5-4. 목록·검색·필터

- 검색은 목록 상단에 배치한다.
- 결과 개수와 적용 중인 필터를 보여준다.
- 데스크톱 필터는 목록 위 또는 왼쪽, 모바일 필터는 버튼·칩·바텀시트로 제공한다.
- 카드 전체가 클릭된다면 hover, focus, 커서 등으로 상호작용을 알린다.
- `자세히 보기`만 반복하지 말고 `걷기 챌린지 자세히 보기`처럼 목적을 알 수 있게 한다.

## 6. 반응형·시각 기준

다음 값은 현재 프로젝트의 고령 사용자 접근성을 고려한 기본값이다. 기존 디자인 토큰이 있으면 토큰을 재사용한다.

| 항목 | 권장 기준 |
|---|---|
| 기본 본문 | 18px 이상, 현재 구현의 20px 기준 유지 가능 |
| 보조 설명 | 가능하면 16px 이상 |
| 본문 줄 높이 | 1.5~1.7 |
| 버튼·입력 높이 | 최소 48px |
| 모바일 주요 버튼 | 가능한 경우 가로 전체 너비 |
| 콘텐츠 간격 | 4, 8, 16, 24, 32, 48, 64px 체계 |
| 긴 폼·본문 폭 | 약 640~800px |
| 전체 콘텐츠 최대 폭 | 약 1200px 전후 |
| 일반 텍스트 명도 대비 | 최소 4.5:1 |
| 키보드 초점 | 배경과 분명히 구별되는 2px 이상 외곽선 |

- 폰트는 Pretendard, Noto Sans KR 등 읽기 쉬운 한글 산세리프 한 종류를 기본으로 한다.
- 글자 굵기를 너무 많이 만들지 않는다.
- 한 화면에서 정렬 기준을 자주 바꾸지 않는다.
- 색상, 둥근 모서리, 그림자보다 여백과 정보 위계를 먼저 맞춘다.
- 모바일에서 가로 스크롤은 표·그래프처럼 불가피한 경우에만 허용한다.
- hover에만 의존하는 정보나 기능을 만들지 않는다.

## 7. 접근성 필수 기준

- 페이지 시작 부분에 본문 바로가기 링크를 제공한다.
- 모든 기능은 키보드만으로 사용할 수 있어야 한다.
- 탭 이동 순서는 화면의 읽기 순서와 일치해야 한다.
- 키보드 초점 표시를 제거하지 않는다.
- 모든 입력에 코드상으로 연결된 `<label>`을 제공한다.
- 제목은 `h1 → h2 → h3`의 논리적 순서를 유지한다.
- 의미 있는 이미지에 대체 텍스트를 제공한다.
- 장식 이미지는 빈 대체 텍스트를 사용한다.
- 색상만으로 선택, 성공, 오류, 위험을 구분하지 않는다.
- 자동 재생되는 소리와 불필요한 자동 슬라이드를 사용하지 않는다.
- 애니메이션에는 정지 수단을 제공하고 `prefers-reduced-motion`을 존중한다.
- 오류가 발생한 위치와 수정 방법을 텍스트로 알려준다.
- 도움말이나 고객센터는 모든 주요 화면에서 비슷한 위치로 접근할 수 있어야 한다.
- 한국어 화면의 문서 언어를 `lang="ko"`로 선언한다.
- 아이콘만 있는 버튼에는 `aria-label` 등 접근 가능한 이름을 제공한다.

국가표준 한국형 웹 콘텐츠 접근성 지침 KWCAG 2.2를 최소 기준으로 사용한다.

## 8. 문장 작성 기준

- 사용자가 쓰는 쉬운 한국어를 사용한다.
- 한 문장에는 한 가지 내용만 담는다.
- 전문용어가 필요하면 먼저 쉬운 표현을 쓰고 괄호로 용어를 덧붙인다.
- 숫자에는 단위와 기준 시점을 함께 표시한다.
- 위험을 과장하거나 확정적으로 표현하지 않는다.
- 같은 개념에 여러 이름을 섞지 않는다.
  - 예: `건강 기록`, `건강정보`, `검진 기록` 중 화면 목적에 맞는 표준 이름을 정해 일관되게 사용
- 시스템 코드, API 오류 코드, 모델 내부 필드명을 사용자에게 그대로 노출하지 않는다.

## 9. Codex 작업 절차

Codex가 UI 변경을 요청받으면 다음 순서로 작업한다.

1. 변경 대상의 사용자와 화면 목적을 한 문장으로 정리한다.
2. 관련 요구사항, 안전 문구, API 계약을 확인한다.
3. 기존 컴포넌트와 디자인 토큰을 우선 재사용한다.
4. 정상 상태뿐 아니라 로딩·빈 상태·오류·성공 상태를 함께 구현한다.
5. 데스크톱과 모바일 레이아웃을 모두 확인한다.
6. 키보드 조작, 초점, 레이블, 대비, 터치 영역을 확인한다.
7. 의료 안전 문구와 적합성 분기가 유지되는지 테스트한다.
8. 기능 변경이면 관련 테스트와 문서를 함께 갱신한다.

Codex는 요청이 모호하더라도 임의로 새로운 의료 기능, 건강정보 수집 항목, 개인별 치료 조언을 추가하지 않는다.

## 10. 완료 기준 체크리스트

### 목적과 흐름

- [ ] 화면의 주 목적과 주 버튼이 하나로 식별된다.
- [ ] 제목과 첫 문단만 읽어도 다음 행동을 이해할 수 있다.
- [ ] 이전·취소·닫기 동작이 예상대로 작동한다.
- [ ] 로그인 전후 내비게이션이 자연스럽게 전환된다.

### 입력과 상태

- [ ] 모든 입력에 화면에 보이는 레이블이 있다.
- [ ] 필수 여부, 단위, 허용 형식을 입력 전에 알 수 있다.
- [ ] 오류 위치와 수정 방법을 구체적으로 보여준다.
- [ ] 오류 후 올바른 기존 입력값이 유지된다.
- [ ] 로딩·성공·오류·빈 상태·재시도 화면이 있다.

### 반응형과 접근성

- [ ] 모바일에서 가로 스크롤이나 잘림이 없다.
- [ ] 주요 버튼과 입력 영역 높이가 48px 이상이다.
- [ ] 텍스트 대비가 4.5:1 이상이다.
- [ ] 키보드만으로 전체 흐름을 완료할 수 있다.
- [ ] 초점 위치가 항상 보인다.
- [ ] 색상을 보지 않아도 상태와 결과를 이해할 수 있다.
- [ ] 이미지와 아이콘에 적절한 접근 가능한 이름이 있다.

### 의료·개인정보 안전

- [ ] 결과를 진단·확정 발병률·치료 효과로 표현하지 않는다.
- [ ] 고위험·경고 상황에서 의료기관 안내가 먼저 보인다.
- [ ] 약물 시작·중단·용량 변경을 권하지 않는다.
- [ ] 서비스에 필요하지 않은 개인정보를 추가로 요구하지 않는다.
- [ ] 동의 목적·항목·보유기간·철회 방법을 확인할 수 있다.
- [ ] 선택 동의를 거절해도 핵심 서비스가 부당하게 차단되지 않는다.
