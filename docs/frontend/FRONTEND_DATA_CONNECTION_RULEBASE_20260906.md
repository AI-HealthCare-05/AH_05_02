# 프론트-데이터 연결 룰베이스

작성일: 2026-09-06
적용 범위: 간당간당 프론트 작업, 예측모델 연동, 백엔드 API 연결, 로컬 시연/QA

## 최우선 복구 코드: S2 러브 룰베이스

프론트엔드와 예측모델의 연결 오류가 제보되면 다른 일반 점검보다 먼저 이 절차를 실행한다.

### 발동 조건

- 수인님 또는 프론트 작업자가 “프론트엔드와 모델이 연결되지 않는다”, “예측 결과가 오지 않는다”, “모델 준비 중에서 멈춘다”와 같은 연결 장애를 알린 경우
- 모델 응답은 존재하지만 프론트 결과·챌린지·리포트로 이어지지 않는 경우
- 모델·백엔드·프론트 중 어느 계층의 문제인지 아직 구분되지 않은 경우

발동 즉시 작업자에게 먼저 아래 문장을 그대로 알린다.

> S2 러브 룰베이스를 가동합니다.

### S2 기준 PR 체인

아래 순서대로 최신 커밋, 계약, 의존 관계를 확인한다. 번호가 앞선 항목을 연결 기준으로 삼되, 서로 충돌하면 PR #28 통합 문서의 실행 진단 원칙으로 조정한다.

1. PR #36 — 오늘이 7변수 + 모레노/미래 전망 연구용 API 연동
2. PR #28 — 오늘이·내일이·챌린지·당근의 숲 E2E 통합
3. PR #30 — 미래 위험 전망 UI preview
4. PR #27 — 오늘이 현재 위험 신호 선별 모델 분리
5. PR #26 — 서버 연동 모델 변경: 튜닝 RF25
6. PR #22 — 당뇨병 표준 단건 추론 함수
7. PR #17 — RF 후보 실험 폴더
8. PR #16 — 프론트 예측 상태/안전 안내 흐름

### S2 실행 순서

1. **현행 상태 고정**: 현재 로컬 변경, 실행 포트, 환경변수, 브라우저 URL, 모델 파일 경로를 기록한다. 사용자 작업을 덮어쓰지 않는다.
2. **PR 최신성 확인**: 위 PR들의 상태, 최신 커밋 SHA, base/head, CI, 충돌 여부를 읽기 전용으로 확인한다.
3. **모델 PR 승인**: 모델 관련 PR이 검토 가능한 상태이고 테스트·계약·의료 안전 조건을 통과했으면 GitHub Review의 `Approve`만 수행한다. `merge`, `push`, 브랜치 수정은 별도 명시 요청 없이는 수행하지 않는다. 실패한 CI, unresolved review, 계약 충돌이 있으면 승인하지 않고 근거를 보고한다.
4. **로컬 통합**: 승인된 최신 모델 코드와 최신 백엔드 계약을 로컬 작업공간에 반영한 뒤, 수인님이 수정 중인 프론트엔드의 요청·응답 매핑을 연결한다. 사용자 변경은 보존한다.
5. **계약 추적**: `프론트 입력 → 요청 DTO → 백엔드 라우터/서비스 → 모델 입력 → 모델 출력 → 응답 DTO → 프론트 표시`를 한 필드씩 대조한다.
6. **#28 기준 실행 진단**: PR #28 통합 문서의 실행 순서와 E2E 흐름을 기준으로 인증, 건강정보, 예측 작업, 결과 표시, 챌린지, 당근의 숲까지 확인한다.
7. **결과 보고**: 성공 여부, 사용한 PR/SHA, 실행 환경, 통과한 검사, 남은 위험을 보고한다. 오류가 있으면 반드시 아래 S2 오류 코드와 추론 근거를 함께 제공한다.

### GitHub 변경 경계

- 평상시에는 기존 원칙대로 GitHub를 수정하지 않고 로컬에서만 작업한다.
- S2 발동 중 허용되는 원격 변경은 검증을 통과한 **모델 관련 PR의 Review 승인**뿐이다.
- PR 병합, 브랜치 push, 코드 수정, PR 본문 변경, 리뷰 dismiss는 S2의 자동 권한에 포함하지 않는다.
- GitHub 로그인·권한 부족 또는 보호 규칙 때문에 승인할 수 없으면 `S2-GH-001`로 보고하고 로컬 연결·진단은 계속한다.

### S2 오류 코드

| 코드 | 계층 | 의미 | 우선 확인할 추론 근거 |
| --- | --- | --- | --- |
| `S2-GH-001` | GitHub | PR 상태/권한 때문에 승인 불가 | 인증, review 권한, draft, CI 실패, 충돌, unresolved review |
| `S2-SRC-001` | 소스 | 기준 PR 또는 최신 SHA 불일치 | fetch 상태, base/head, 로컬 반영 SHA |
| `S2-MDL-001` | 모델 | 모델 파일 또는 provider 로드 실패 | artifact 경로, joblib 호환성, 모델 버전, feature 수 |
| `S2-MDL-002` | 모델 | 모델 입력 계약 불일치 | 변수명·순서·타입·누락값·범주 인코딩 |
| `S2-API-001` | 백엔드 | 라우터/엔드포인트 연결 실패 | prefix, HTTP method, 등록된 router, 서버 포트 |
| `S2-API-002` | 백엔드 | 요청/응답 DTO 불일치 | `422`, 필드 required 여부, enum, ID 타입 |
| `S2-AUTH-001` | 인증 | 토큰 또는 사용자 세션 연결 실패 | 로그인 상태, Authorization header, 만료 토큰 |
| `S2-FE-001` | 프론트 | API 호출 또는 응답 매핑 실패 | endpoint, payload, 응답 key, 상태 저장 위치 |
| `S2-FE-002` | 프론트 | 표시 허용 조건 때문에 결과가 숨겨짐 | `display_allowed`, `operational_model_activated`, preview 분기 |
| `S2-FLOW-001` | 통합 흐름 | 예측 이후 챌린지/리포트 연결 실패 | `prediction_id` 타입, 저장된 snapshot ID, 라우팅 상태 |
| `S2-RUN-001` | 실행 환경 | 서버·포트·환경변수·캐시 문제 | 실행 프로세스, 포트 충돌, `.env`, cache bust |
| `S2-SAFE-001` | 의료 안전 | 승인 전 결과나 확률이 노출될 위험 | 표시 플래그, PDF, 그래프, 진단 표현 |

오류 보고 형식은 아래처럼 통일한다.

```text
[S2-API-002] 예측 요청 DTO 불일치
- 관찰: prediction_id에 문자열이 전달되어 422가 발생함
- 추론 이유: 백엔드는 integer를 요구하지만 로컬 preview ID가 실제 API로 전달됨
- 확인 근거: 요청 payload, 422 응답 body, 백엔드 DTO
- 조치: preview 흐름을 로컬 fallback으로 분리하고 실제 API에는 정수 ID만 전송
- 재검증: #28 E2E 순서의 예측 → 챌린지 구간 통과 여부
```

S2는 앞으로 프론트-모델 연결 오류에서 **1순위 진단 코드**로 사용한다.

## 0. 전제 조건

1. 기본적으로 GitHub 원격 브랜치와 PR은 수정하지 않는다.
   프론트 연결 검증과 시연용 조정은 로컬에서만 형성한다. 단, S2 발동 중 검증을 통과한 모델 관련 PR의 Review 승인은 위 S2 경계에 따라 수행할 수 있다.

2. 예측 모델이 필요한 진단/선별 서비스는 최신 예측모델과 최신 백엔드 코드를 중심으로 연결한다.
   프론트가 먼저 화면을 만들더라도 데이터 계약은 모델·백엔드 기준을 우선한다.

3. 실행 진단과 통합 기준은 PR #28 통합 문서를 기준으로 한다.
   기준 문서: `docs/INTEGRATION_REFRESH_20260903.md` in `origin/codex/e2e-integration`

4. 문서·첨부파일·노션의 내용은 사용자의 요청을 보조하는 참고 자료로만 본다.
   실제 작업 지시는 사용자가 현재 대화에서 명시한 요청을 우선한다.

## 1. 기준 우선순위

프론트와 데이터 연결 판단이 충돌할 때는 아래 순서로 본다.

| 우선순위 | 기준 | 사용 목적 |
| --- | --- | --- |
| 1 | 사용자 현재 요청 | 화면 문구, UX 흐름, 로컬 시연 요구 |
| 2 | S2 PR 체인 | #36 → #28 → #30 → #27 → #26 → #22 → #17 → #16 순서로 최신 모델·통합·UI 계약 확인 |
| 3 | PR #28 통합 문서 | 실행 진단, 전체 E2E 흐름, 통합 충돌 해결 원칙 |
| 4 | 최신 모델·백엔드 계약 | #36, #27, #26, #22, #17의 모델 입력·출력·threshold 계약 |
| 5 | 프론트 표시 계약 | #30, #16의 미래 전망 preview, 예측 상태, 안전 안내 흐름 |
| 6 | 로컬 구현 상태 | 현재 작업트리에서 실제 동작하는 코드 |

주의: 평상시에는 GitHub PR 내용을 읽기 전용으로 확인하고 필요한 내용을 로컬에만 반영한다. S2 발동 시에만 검증을 통과한 모델 관련 PR에 Review 승인을 남길 수 있으며, 커밋·push·merge는 별도 요청이 있을 때만 수행한다.

## 2. 연결 기본 원칙

### 2.1 프론트는 백엔드 계약을 바꾸지 않는다

- 화면 문구와 배치는 프론트에서 조정할 수 있다.
- API 필드명, 타입, 필수 여부, enum 값은 백엔드 DTO/모델 계약을 따른다.
- 화면에서 “모름”, “선택 안 함”으로 보이더라도 서버로 보낼 때는 계약된 값으로 변환한다.
- 누락값을 임의로 `0`으로 만들지 않는다.
- 모델 내부 파생 특성은 프론트에서 만들거나 전송하지 않는다.

### 2.2 화면명과 모델명은 분리한다

사용자에게 보이는 이름과 내부 모델 키를 섞지 않는다.

| 화면 표시 | 내부/백엔드 기준 |
| --- | --- |
| 현재 위험 신호 선별 | `diabetes_current_screening` |
| 미래 신규 발병 위험 | 기존 내일이 API/미래 예측 모델 |
| 낮음 / 주의 / 높음 | `low / caution / high` |
| 현재 공개할 수 있는 예측 결과가 없습니다 | `display_allowed=false` |

프론트 화면에는 `오늘이`, `내일이`, `모레노` 같은 내부 가칭을 노출하지 않는다.

### 2.3 승인 전 결과는 안전하게 막는다

- `display_allowed=false`이면 확률, 점수, 위험요인, 그래프를 노출하지 않는다.
- `operational_model_activated=false`이면 운영 모델처럼 표현하지 않는다.
- 로컬 시연에서만 결과 모양을 보여줄 때는 `preview`, `demo`, `local` 상태를 별도로 둔다.
- 로컬 시연 플래그를 운영 표시 플래그로 바꾸지 않는다.
- PDF에도 승인 전 수치·확률·위험요인을 임의로 넣지 않는다.

## 3. 모델별 연결 룰

### 3.1 현재 위험 신호 선별

- 모델 키는 `diabetes_current_screening`으로 분리한다.
- 현재 위험 신호 선별은 “현재 확인이 필요한 신호”로만 표현한다.
- 진단 확정, 치료 판단, 개인 확정 발병확률처럼 보이게 쓰지 않는다.
- 입력 경계, 적용 연령, 의료 검토가 끝나기 전까지 기본은 `display_allowed=false`이다.
- RF25 또는 shared7 결과가 `low/caution/high`로 오면 프론트는 `낮음/주의/높음`으로 표시할 수 있어야 한다.

### 3.2 미래 신규 발병 위험

- 기존 내일이 API와 입력 계약은 유지한다.
- 현재 판정 점수와 미래 발생 점수를 평균하거나 하나의 확률처럼 합치지 않는다.
- `cumulative_risk_signal`은 개인 확정 발병확률처럼 표시하지 않는다.
- 생존 앙상블의 2·4·6년 값은 아래 조건이 모두 충족되기 전까지 그래프로 노출하지 않는다.
  - `risk_curve_status=available`
  - `lower/upper` 구간 존재
  - calibration 정보 존재
  - 의료 안전 검토 완료
  - 운영 표시 승인 완료

### 3.3 모델 메타데이터

백엔드 응답에서 아래 필드를 받을 수 있는 구조를 프론트에 유지한다.

- `model_key`
- `task_type`
- `model_version`
- `threshold_scope`
- `threshold_version`
- `model_artifact_digest`
- `display_allowed`
- `operational_model_activated`
- `risk_curve_status`

이 값들은 화면에 전부 보여주기 위한 값이 아니라, 표시 가능 여부와 QA 추적을 위한 기준값이다.

## 4. 입력 데이터 룰

### 4.1 입력 단계 구조

건강정보 입력은 다음 순서로 관리한다.

1. 기본 정보 입력
2. 생활습관 입력
3. 세부 건강정보
4. 입력 내용 확인

### 4.2 공통 정보 재사용

공통 사용자 정보는 재사용하되, 모델별 코드 변환은 분리한다.

| 공통 입력 | 사용 방식 |
| --- | --- |
| 생년월일 | 나이 계산 |
| 키/체중 | BMI 계산 |
| 성별 | 모델별 코드로 변환 |
| 허리둘레 | 현재 선별 입력에 사용 가능 |
| 흡연/음주/운동 | 생활습관과 세부 건강정보에서 중복 질문되지 않게 한 공간에서 관리 |

### 4.3 오늘이 추가 입력 스냅샷

현재 위험 신호 선별에 필요한 추가 입력은 건강정보 흐름 안에서 받는다.
사용자-facing 이름은 “오늘이 추가 정보”처럼 내부 모델명이 드러나는 표현을 피하고, “세부 건강정보”로 둔다.

서버 연결 준비 시 예상 API:

```http
POST /api/v1/current-screening-inputs
```

오늘이 요청에는 입력 스냅샷 ID를 포함한다.

```json
{
  "checkup_id": 123,
  "model_key": "diabetes_current_screening",
  "current_screening_input_id": 456
}
```

### 4.4 전송 금지 항목

아래 값은 모델 내부 파생 특성이므로 프론트 API나 입력 테이블에 저장·전송하지 않는다.

- `waist_height_ratio`
- `waist_was_estimated`
- `waist_expected_cm`
- `waist_minus_expected_cm`

## 5. API 연결 룰

### 5.1 실제 API와 로컬 시연 API를 분리한다

- 실제 API 연결은 백엔드 라우터와 DTO가 존재할 때만 사용한다.
- 로컬 시연 API는 localhost/demo 환경에서만 사용한다.
- 시연용 응답은 실제 운영 승인 결과처럼 저장하거나 표시하지 않는다.
- 시연용 코드에는 주석 또는 함수명으로 `demo`, `preview`, `local` 성격이 드러나야 한다.

### 5.2 ID 타입을 보존한다

백엔드가 정수 ID를 요구하는 곳에는 문자열 시연 ID를 보내지 않는다.

예:

- 잘못된 예: `prediction_id: "local-demo-junhyuk"`
- 올바른 처리:
  - 실제 백엔드 호출이면 정수 `prediction_id`만 전송
  - 로컬 시연이면 챌린지 추천도 로컬 fallback으로 처리
  - 문자열 ID가 필요한 경우 별도 `preview_prediction_key` 같은 필드로 분리

### 5.3 실패 상태를 화면에서 구분한다

같은 “서버 오류”로 뭉개지 말고 원인을 구분한다.

| 상태 | 프론트 처리 |
| --- | --- |
| `422 ML_INPUT_INVALID` | 입력값 확인/수정 안내 |
| `503 MODEL_UNAVAILABLE` | 모델 준비 중/시연 fallback 안내 |
| `503 MODEL_CONTRACT_INVALID` | 모델 계약 불일치 안내, 운영 결과 미노출 |
| 네트워크 실패 | 서버 실행 여부 확인 안내 |
| 인증 실패 | 로그인 화면으로 이동 |
| display 차단 | 예측 결과 미제공 안내 |

## 6. 화면 흐름 룰

### 6.1 로그인 전

- 상단 네비게이션에는 로고, 회원가입, 로그인만 노출한다.
- 건강정보 입력, 챌린지, 대시보드, 당근의 숲, 마이페이지는 노출하지 않는다.
- 로그인 필요한 버튼을 눌렀다면 로그인 화면으로 보낸다.

### 6.2 로그인 후

- 상단 구조는 기존 5개 탭바를 사용한다.
  - 홈
  - 챌린지
  - 리포트
  - 함께하기
  - 건강도구
- 당근의 숲은 최상단 독립 메뉴가 아니라 함께하기 안의 하위 기능으로 둔다.

### 6.3 신규 가입 직후

신규 가입자는 기존 로그인 사용자와 같은 탭을 바로 보여주기 전에 아래 흐름을 우선 확인한다.

1. 건강정보 처리 동의
2. 이용 대상 확인
3. 기본 정보 입력
4. 생활습관 입력
5. 세부 건강정보
6. 입력 내용 확인
7. 분석 상태
8. 결과 확인
9. 챌린지 선택 또는 대시보드

적용 연령 밖, 긴급 증상, 당일 진료 필요, 기진단 여부 등은 결과 화면으로 넘기기 전에 팝업으로 안내한다.

## 7. 팝업/분기 룰

아래 분기는 프론트 QA 때 반드시 확인한다.

| 분기 | 표시 |
| --- | --- |
| 만 14세 미만 | 회원가입 불가 팝업 |
| 예측모델 적용 연령 밖 | 예측 결과 미제공 안내 팝업 |
| 긴급 증상 있음 | 119/응급 안내 팝업 |
| 당일 진료 필요 | 의료기관 안내 팝업 |
| 이미 당뇨 진단 받음 | 일반 건강정보/의료진 관리 우선 안내 팝업 |
| 건강정보 처리 동의 안 함 | 동의 필요 안내 팝업 |

팝업 선택 후 같은 선택지를 다시 누르면 팝업이 사라지도록 한다.

## 8. QA 체크 순서

프론트-데이터 연결을 수정한 뒤에는 아래 순서로 본다.

1. 현재 서버가 실제 백엔드인지 로컬 시연 서버인지 확인한다.
2. 브라우저 URL과 cache query를 확인한다.
3. 로그인 전/후 네비게이션이 분리되는지 확인한다.
4. 신규 가입 플로우와 기존 로그인 플로우가 섞이지 않는지 확인한다.
5. 건강정보 입력값이 화면 이동 후 유지되는지 확인한다.
6. 선택/모름/null 값이 API 계약에 맞게 변환되는지 확인한다.
7. 분석 상태 화면에서 성공/실패/모델 준비중 상태가 구분되는지 확인한다.
8. 결과 화면에서 display 차단 로직이 유지되는지 확인한다.
9. 챌린지 추천에서 demo string ID가 실제 API로 넘어가지 않는지 확인한다.
10. 리포트/PDF에서 승인 전 수치가 임의로 들어가지 않는지 확인한다.
11. 모바일 380px 전후에서 버튼·카드·입력폼이 겹치지 않는지 확인한다.

## 9. 로컬 검증 명령

프론트 또는 API 연결을 수정한 뒤 최소 아래를 확인한다.

```bash
node --check src/frontend/app.js
python -m compileall app
pytest tests/test_prototype.py -q
```

백엔드까지 띄워 확인할 때는 현재 포트 충돌을 먼저 본다.

```bash
docker compose ps
```

로컬 시연 서버는 운영 서버로 오해하지 않게 포트와 실행 옵션을 분리한다.

예:

```bash
DEMO_MODE=true python -m uvicorn app.main:app --host 127.0.0.1 --port 8016
```

## 10. 자주 끊기는 지점과 즉시 점검표

| 증상 | 먼저 볼 곳 | 원칙 |
| --- | --- | --- |
| 모델 준비중만 표시 | 모델 파일 경로, provider, `MODEL_UNAVAILABLE` | 시연이면 demo fallback, 운영이면 미노출 |
| 챌린지 목록 불러오기 실패 | `prediction_id` 타입, challenge API 응답 | demo string ID를 실제 API에 보내지 않기 |
| `prediction_id` integer 오류 | 챌린지 시작 payload | 실제 API에는 정수 ID만 |
| 결과 그래프가 안 보임 | `display_allowed`, `risk_curve_status` | 승인 전 그래프 미노출이 정상일 수 있음 |
| 입력 저장 후 값 사라짐 | local state/session storage/API snapshot | 입력 단계별 state 소유자 하나로 통일 |
| 이전 JS/CSS가 계속 보임 | `index.html` cache bust | 수정 후 cache query 갱신 |
| 로그인 전 메뉴 혼란 | nav auth state | 비로그인은 회원가입/로그인만 |

## 11. 작업 전 체크 문장

프론트 연결을 수정하기 전에는 아래 문장을 기준으로 판단한다.

> 이 화면은 최신 모델·백엔드 계약을 깨지 않고, 로컬 시연과 실제 운영 표시를 구분하며, 사용자가 진단 확정이나 발병확률로 오해하지 않게 보여주는가?

이 질문에 “예”라고 답할 수 없으면 먼저 데이터 계약, display flag, 로컬 fallback 범위를 확인한 뒤 수정한다.
