# 9월 9일 FE 연동 기준 백엔드 확인·요청 사항

확인일: 2026-09-09

기준: PR #42 (`codex/fe-followup-20260909`) 및 `codex/e2e-integration`

보안: `.env`, API 키, 비밀번호, 개인정보는 확인하거나 문서에 포함하지 않음

## 팀 공지용 요약

> PR #42의 실패 원인은 백엔드 오류가 아니라 최신 프론트 UX와 오래된 회귀 테스트의 불일치였음. 현재 UX는 되돌리지 않고 테스트 계약을 갱신했으며, 로컬에서 Python 362개 통과·4개 건너뜀, 프론트 93개 통과, Ruff 검사 통과를 확인함. 아래 항목부터는 프론트만으로 완료할 수 없거나 실제 백엔드 응답 검증이 필요한 사항임. 특히 지난 4주·전체 리포트, 현재 선별용 세부 입력, 사진 인증, 진행 중 회차의 챌린지 변경, 숲 슬로건 저장 계약 확인이 우선 필요함.

## 1. 이번 수정으로 프론트에서 해결한 항목

아래 항목은 백엔드 조치 요청에서 제외함.

- PR #42의 기존 문자열·DOM 기준 회귀 테스트를 현재 사용자 흐름 기준으로 수정함.

- 이번 주 리포트의 `challenge_details`를 배열 안전하게 처리하고 상세 기록 UI를 검증함.
- 생활습관 지도와 당근의 숲 진입 화면을 현재 구조 기준으로 검증함.
- 내일이 결과의 기존 그래프 틀을 복원하되 `age_risk_forecast.points` 중 정확히 2년 값만 표시함.
- 2년 데이터가 없으면 그래프 영역에 `전망 데이터 준비 중`을 표시함.
- 모레노 호출과 생활습관 유지·개선 시나리오는 복원하지 않음.
- 당근의 숲 공동 보상 기준을 고정 숫자가 아닌 서버의 `today.target` 값으로 검증함.

## 3. 상세 확인 요청

### 3-1. 지난 4주·전체 리포트

프론트가 호출하는 경로:

- `GET /api/v1/reports?period=four-week`
- `GET /api/v1/reports?period=all`
- `GET /api/v1/reports/{report_id}/cycles?cursor={cursor}`

현재 확인:

- 프론트 결과 화면과 `next_cursor` 추가 조회는 구현함.
- 현재 통합 코드에서는 위 라우터를 확인하지 못함.
- 기존 `GET /api/v1/weekly-reports/current`와 `GET /api/v1/weekly-reports/current/pdf`는 유지함.

요청:

- 구현된 커밋 SHA·브랜치·PR 공유 필요함.
- `period`, `status`, `report_id`, `headline`, `summary`, `buckets`, `participation_days`, `eligible_days`, `cycles.items`, `cycles.next_cursor`, `generated_at` 계약 확인 필요함.
- 빈 결과·없는 리포트·잘못된 cursor의 404/422 기준 확인 필요함.
- 이번 주 PDF만 지원하는 현재 범위를 유지함. 지난 4주·전체 PDF는 별도 계약 전 활성화하지 않음.

### 3-2. 현재 위험 선별용 세부 건강정보

프론트 호출:

- `POST /api/v1/current-screening-inputs`

현재 확인:

- 통합 백엔드에 해당 라우터가 없어 404가 발생함.
- 프론트는 404를 저장 성공으로 위장하지 않음.

결정 요청:

1. 별도 스냅샷 API를 구현함.
2. `POST/PATCH /api/v1/health-checkups` DTO에 오늘이 입력 필드를 통합함.
3. 모델 최종 입력 계약에서 사용하지 않는 항목을 제거함.

함께 확정할 값:

- 실제 사용 변수·타입·단위·결측 처리
- 입력 기준일과 원본 `health_checkup_id`
- 예측 작업에 스냅샷 ID를 전달하는 방식
- 재예측 시 이전 입력 스냅샷 보존 여부

### 3-3. 내일이 2년 전망

프론트 표시 조건:

- `display_allowed !== false`
- `age_risk_forecast.points`가 배열임
- 항목의 `years_from_now`가 숫자 `2`임
- 2년 항목에 표시 가능한 위험 값이 있음

백엔드·모델 요청:

- 내일이 공개 가능 응답에 정확한 2년 point 포함 필요함.
- point의 필드명·값 단위 확정 필요함. 예: `years_from_now`, `risk_probability` 또는 최종 합의 필드.
- `model_version`, `promotion_status`, `display_allowed`, `preview_only`, `risk_curve_status`, `calibration_status` 최종 기준 공유 필요함.
- 공개 불가 상태에서는 수치·위험 범주를 보내더라도 프론트가 노출하지 않는 현재 안전 규칙을 유지함.
- 모레노 전망과 생활습관 유지·개선 시나리오는 MVP 응답·화면 범위에서 제외함.

### 3-4. 사진형 챌린지

프론트 호출:

- `POST /api/v1/user-challenges/{user_challenge_id}/photo-verifications`

현재 확인:

- 통합 백엔드에는 없고 별도 Draft 작업에만 있는 것으로 확인함.
- 통합 전 사진형 후보가 내려오면 실제 제출이 404가 될 수 있음.

요청:

- 관련 PR을 통합하거나, 통합 전 카탈로그에서 사진형 후보를 제외함.
- `review_status`, `challenge_completed`, 실패 코드, 재시도 가능 여부를 확정함.
- 사진 처리·보관·삭제·외부 분석 사용 고지를 정책과 함께 확정함.

### 3-5. 진행 중 챌린지 구성 변경

사용자 요구:

- 처음 1개 선택 후 같은 4주 회차에서 2개 또는 3개로 변경하고 싶음.

현재 확인:

- 회차 생성·현재 회차 조회·상태 변경 API는 존재함.
- 진행 중 회차의 챌린지 목록 추가·제거·교체 API는 없음.

요청:

- 진행 중 변경을 허용할지 정책 결정 필요함.
- 허용 시 `PATCH /api/v1/challenge-cycles/{cycle_id}/challenges` 형태의 계약 검토 필요함.
- 추가 항목 시작일, 제거 항목의 과거 기록, 달성률, 리포트 반영, 최대 선택 개수 기준 확정 필요함.

### 3-6. 건강정보 동의 철회

연결된 API:

- `GET /api/v1/consents`
- `POST /api/v1/consents`
- `PATCH /api/v1/consents/{consent_id}/withdraw`

프론트 처리:

- 철회 직후 신규 건강정보·예측·챌린지 화면을 차단함.
- 재동의 화면을 제공함.

백엔드·정책 요청:

- 철회 시 진행 중 챌린지 회차를 즉시 종료할지 확정함.
- 기존 건강정보·예측 결과의 보관 기간·파기·열람 정책 확정 필요함.
- 재동의 시 새 동의 이력을 만드는지 확정함.
- 철회 직후와 재로그인 후에도 서버가 신규 저장·예측·회차 생성을 차단하는지 실제 응답 검증 필요함.

### 3-7. 당근의 숲·게임 데이터

누락 확인 API:

- `PATCH /api/v1/forest/spaces/{group_id}/slogan`

요청:

- 슬로건 요청 DTO·응답·길이·공백·금칙어·권한·401/403/404 계약 필요함.
- 당근 재화·거래·아이템·보유 수량·장착은 게임 API, 숲 이름·슬로건·오브젝트·공동 보상은 숲 API로 관리할지 확정함.
- `ForestAvatar.carrot_balance`, `ForestInventory`와 게임 API 데이터의 중복 제거 또는 역할 분리 필요함.
- 구매·보상 중복 요청 방지와 거래 원장·잔액의 원자적 갱신 기준 필요함.
- 새로고침·재로그인·다른 기기에서 동일 데이터가 복원되는지 실제 API E2E 필요함.

### 3-8. 예측 대기·시간초과

프론트 완료:

- 오늘이·내일이를 병렬 요청함.
- 성공한 결과를 유지하고 실패한 모델만 재시도함.
- 대기·실패·시간초과·빈 결과를 구분함.

백엔드·Worker 요청:

- 작업 생성 후 큐 대기시간과 Worker 시작 후 추론시간의 제한을 분리함.
- `queued_at`, `started_at`, `completed_at`, `worker_name`, `attempts`, `error_code`, `retryable`, `retry_after_seconds`를 같은 `job_id` 기준으로 유지함.
- Worker 시작 시 모델·Manifest·SHA·필수 라이브러리를 사전 검증함.
- Redis 장애·Worker 미기동·모델 누락·계약 오류·시간초과를 실제 통합 환경에서 재현함.
