# 9/7 우선순위 재점검 — 큐 복구 이후

대상: `AH_05_02-s2-api002`, `http://127.0.0.1:8022/`.
이 문서가 앞선 `queued`/전체 E2E 미완료 기록보다 최신이다. 의료·모델 운영 승인을 의미하지 않는다.

## 1. 분석 queued — 로컬 복구 완료

- **S2-RUN-001:** API는 다른 프로젝트의 Redis 6379, 프로젝트 워커는 게시 포트 6380을 사용했다. 6379 스트림은 메시지 9개, 소비자 그룹이 없었다.
- **S2-SRC-001:** 6380으로만 바꾸면 기존 Docker 워커가 메시지를 소비하지만, 구버전 워커는 `ai_jobs`를 갱신했다. 현재 API는 `prediction_jobs`를 조회하므로 여전히 queued로 남았다.
- 8022와 같은 코드의 로컬 워커를 실행하고, 프로젝트 Redis 6380의 **전용 스트림 `ai:jobs:local8022` / 그룹 `local8022-workers`**로 분리했다.
- 로컬 워커는 필요한 테이블/컬럼을 읽기 전용으로 확인한 후 기동한다. `prepare_schema=False`로 스키마 생성·변경을 실행하지 않는다. 다른 Docker 워커와 기존 메시지는 이동·삭제하지 않았다.
- 기존에 멈춘 분석 요청을 자동 재처리한 것은 아니다. 사용자 화면에서 새로 분석해야 한다.
- 모델 파일 SHA256을 전달 기준과 대조했다. `S2_MODEL_RUNTIME_ENABLED`는 해당 로컬 워커의 연구용 추론 실행에만 사용하며 `display_allowed` / `operational_model_activated`를 강제로 true로 바꾸지 않았다.

실행은 로컬 저장소 루트에서 각각 별도 터미널로 한다:

```bash
.venv/bin/python scripts/run_frontend_local_8022.py
.venv/bin/python scripts/run_worker_local_8022.py
```

두 실행기는 기존 DB 설정 로더를 동일하게 사용한다. 키·환경파일 본문을 직접 열거나 출력하지 않았다. 로컬 실행기/worker 변경은 프론트 PR의 백엔드 통합 완료를 뜻하지 않는다.

## 2. 지도 — 사용자 설정 확인 필요

- 실제 병원 15곳·응급기관 10곳의 REST 목록은 성공했다.
- 카카오 JavaScript SDK는 **HTTP 401 / 도메인 접근 거부**, 브라우저에서는 `ERR_BLOCKED_BY_ORB`로 실패했다. SDK 실패 때문에 지도 및 SDK 기반 주소 검색이 함께 실패한다.
- JavaScript 키와 연결된 카카오 앱의 허용 도메인에 `http://127.0.0.1:8022`, `http://localhost:8022` 등록 확인을 요청했다. REST 키를 프론트로 복사하지 않는다.
- 설정 확인 후 지도·마커·주소 검색 실연동을 다시 검사해야 한다. 목록 성공을 지도 성공으로 표시하지 않는다.
- 기준: [Kakao Maps 공식 시작 가이드](https://apis.map.kakao.com/web/guide/).

## 5. PDF 검수 — 다운로드 성공, 완성본 아님

- 실제 파일: `tmp/pdfs/weekly-report-live-20260907.pdf`, A4 1페이지.

- [ ] 기간 시작/종료일 및 상세 수행 기록 필요. 현재/미래 모델 영역을 추가한다면 승인 전 정보 비노출 계약부터 확정.
