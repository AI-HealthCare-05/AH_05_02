# 멘토링 피드백 요약 (멘토님 발언 중심)

## 총평

- 2주 만에 이 정도 완성도를 보여준 팀은 드물다. 회원가입 → 적합성 확인 → 건강정보 입력 →
  예측 결과 → 의료 안내 → 챌린지 → 대시보드로 이어지는 흐름 전체를 갖췄다는 점을 높게 평가.
- 오늘이·내일이를 별도 모델(별도 학습 데이터)로 분리한 설계 판단 자체를 크게 평가함 —
  "코드는 몇 줄 차이일 수 있어도, 역할을 분리했다는 결정이 크다."
- 당근의 숲(게임화 리텐션 장치)의 기획력, 특히 싸이월드 감성을 가져온 부분을 강하게 칭찬.
  당뇨 환자군과 싸이월드 세대가 상당히 겹친다는 점에서 세대 융합·레트로 요소가 리텐션
  증명에 유리하다고 판단.
- "모델 성능도 중요하지만, 이 서비스의 핵심은 지속 가능성(리텐션)"이라는 게 본인 지론.
  "모델 얘기만 하는 사람들 말은 한 귀로 흘려도 된다."

## 최우선 리스크 — 오늘이·내일이 결과 불일치

- 가장 크게 짚은 리스크: **오늘이와 내일이가 서로 다른(모순된) 결과를 줄 가능성.**
  예) 오늘이는 "위험", 내일이는 "안전"으로 나오는 케이스.
- 외부 평가자/비판적인 사람은 이런 불일치 사례 단 한 번만 발견해도 서비스 전체를
  부정적으로 판단할 수 있다고 경고.
- 요청: 두 모델이 어긋날 때의 처리 방식을 설계할 것 (예: 단순 상충 노출 대신 "확인 불가"
  형태의 완충 처리 검토).

## 성능 지표 & 메시징

- RF25 v0.6.1 리콜 수치 오탈자 지적: 94.85% → **93.85%**가 맞음 ("숫자 하나가 엄청난 차이").
- 현재 specificity ~40.66%는 "위험군을 넓게 잡아 놓치지 않기 위한" 설계라는 점을 재확인.
- 핵심 질문: *"양성 경고를 받은 100명 중 진짜 양성이 6명뿐이라면, 나머지 94명에게 어떤
  경험을 줘야 이 모델이 서비스로서 정당화되는가?"*
- 결론: 문구를 **"당뇨 위험이 높습니다"(확정형) → "추가 확인이 필요한 위험 신호가
  확인되었습니다"(완곡형)** 로 바꿀 것. 모델은 진단이 아니라 검사·상담 필요성을 넓게
  선별하는 장치라는 프레이밍을 UX 전반에 심을 것.
- RF25 개선판(recall +4.1%, AUROC 소폭 하락)에 대해: "이건 새 모델이 아니라 threshold만
  바꾼 것" — recall 4% 얻자고 specificity 7%를 희생하는 게 가치 있는지 재검토 필요.
  Threshold를 계속 바꿔가며 비교하지 말고 **고정 후 독립적으로 기록**할 것.

## 모델 공개 전 보완 우선순위 (멘토님 지정 순서)

1. 독립 평가 구조 확보 (threshold를 건드리지 않은 상태의 결과와 비교)
2. Threshold 재검토 — threshold별 Recall/Specificity/**PPV/NPV**/Prevalence/**FP·FN
   카운트** 전부 계산
3. 확률 보정(Calibration)
4. 연령별·성별 하위집단(subgroup) 성능 확인

> 참고: 이 4가지는 지난번에 정리해드린 "5개 항목" 준비자료(confusion matrix, threshold
> 비교표 등)와 방향이 거의 일치함. 멘토님이 채팅으로 별도 체크리스트를 추가로 보내주기로
> 함 — 받는 대로 교차 확인 필요.

## 입력 변수 최적화

- 25개 변수 중 8개 필수 / 17개 선택으로 나눠져 있는 현재 구조를 두고, **선택 변수 하나
  하나를 제거해봤을 때 성능이 크게 무너지는지 일일이 검증**할 것을 요청 (본인 표현으로
  "노가다"이지만 필요한 과정).
- 원칙: "AUPRC 0.001 올리자고 입력 화면 3개를 늘리는 것"은 대체로 가치가 없다 —
  **추가(add)보다 제거(remove)가 맞는 방향.**

## 모레노(장기 예측 모델) 처리 방향

- 내일이(2년, 이진 분류)와 모레노(4·6·18년, survival 구조)를 **가중 평균으로 앙상블하지
  말 것** — 아웃컴 구조 자체가 달라 통계적으로 맞지 않음.
- 2년 지표만이 실질적으로 액션 가능한(actionable) 트리거이며, 4·6년 장기 지표는 서비스
  의미가 크지 않다고 판단.
- **결론: 남은 2주는 오늘이·내일이 두 모델에만 집중, 모레노는 연구용 후순위로 유지.**

## 응급 증상 / 119 안내 기능

- 진짜 응급 상황(의식 저하·소실)에서는 사용자가 앱을 조작해 버튼을 누를 수 있는 상태가
  아니라는 현실적 한계를 지적. 아이디어는 좋으나 UX 재설계 필요.
- 대안 제안: **스마트워치 연동** (멘토님 본인이 과거 삼성 스마트워치 앱 개발 경험 있음).

## QA / 테스트 요청 사항

- **골든 패스 테스트(최우선)**: 정상 상태의 52세 사용자 1명을 실제로 앉혀서 가입 →
  건강정보 입력 → 오늘이/내일이 결과 → 의료기관 안내 → 챌린지 → 대시보드까지 한 번도
  막힘 없이 통과하는지 확인. 옆에서 촬영하며 관찰할 것. ("100% 막힐 것"이라고 단언)
- 288건 자동 E2E 테스트 보유를 높게 평가.
- **실제 모델 아티팩트(가짜 stub 아님)로 개인정보 형태 입력 → 결과 산출까지** 직접
  시연해볼 것을 요청.
- 외부 의료기관 API(카카오 로컬) 실패 시 "위치 확인 불가" 폴백 UX는 잘 되어 있다고 확인.
- 확인됨: 기진단자 재요청 차단 테스트 완료.
- 추가 고민 요청: 범위 안이지만 잘못 입력된 값(연령 오타 등) 처리 — 연령대 사전 확인
  질문 등 이중 검증 장치, 그리고 이상 입력값은 저장/재활용하지 말고 폐기할 것.

## 리텐션 / 온보딩 UX

- 사용자는 계속 "다음에 뭘 해야 하는지" 궁금해한다 — A부터 Z까지 전체 흐름에서 **어떤
  사용자는 완주하고 어떤 사용자는 왜 특정 단계에서 이탈하는지**를 정량적으로 추적할 것
  (클라이언트 플로우 로그를 전체 구간에 심을 것 — 향후 투자 유치 시 자산이 될 수 있음).
- 당근의 숲 보상을 설문 **맨 마지막에 한 번에 몰아주지 말고, 중간중간 분산 배치**할 것.
  입력해야 할 보상이 뭔지 미리 예고(티저)하는 것도 이탈 방지에 도움.
- 입력 변수를 줄이는 것이 곧 이탈률 감소로 이어짐 — 위 "입력 변수 최적화"와 동일한 맥락.

## PoC / 배포 관련

- 다음 주 중 로컬호스트가 아닌 **외부에서 접속 가능한 서버**로 열어둘 것을 제안.
- 실제 당뇨 환자 대상 PoC 진행 권장 — 좋은 피드백이 아니라 **나쁜 피드백을 받겠다는
  마음으로** 진행할 것.
