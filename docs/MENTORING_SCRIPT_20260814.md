## 2. Sprint 1 산출물 보고 (약 1분 20초)

현재 네 가지 산출물은 모두 v1.0 초안을 작성했습니다.

- 요구사항 정의서는 회원·동의, 적합성 확인, 건강정보 입력, AI 예측, 챌린지, 대시보드뿐 아니라 의료·AI 안전, 개인정보보호, 접근성, 성능과 모델 품질 기준까지 정리했습니다.
- 와이어프레임은 서비스 소개부터 적합성 확인, 검진 입력, 예측 결과, 챌린지 선택과 기록, 추적 대시보드까지의 핵심 흐름을 구성했습니다.
- ERD는 건강검진 한 건에 여러 모델 버전의 예측 결과를 보존하고, 4주 챌린지를 별도 사이클로 관리하도록 설계했습니다.
- API 명세서는 `/api/v1`을 기준으로 인증, 동의, 건강검진, 비동기 예측, 챌린지, 대시보드와 후속 조치를 연결했습니다.

문서 초안은 완성했지만 서비스 대상, 모델 출력의 의미, 확장 가능한 저장 구조와 안전한 사용자 흐름이 아직 완전히 합의되지 않았습니다. 지금부터 이 네 영역에 대해 차례로 질문드리겠습니다.

## 3. 서비스 범위에 대한 피드백 (약 2분)

### 3-1. 이용 가능 연령과 주 타깃

현재 저희 서비스의 주 타깃은 65세 이상 고령자입니다. 다만 국민건강영양조사는 만 19세 이상 데이터를 활용할 수 있고, 서비스 자체도 19세 이상 성인이 이용할 수 있도록 열어두는 안을 검토하고 있습니다.

팀의 잠정안은 **서비스 이용 자격은 만 19세 이상**, **핵심 타깃과 접근성 설계 기준은 만 65세 이상**으로 분리하는 것입니다. 모델도 19세 이상 전체, 40세 이상, 65세 이상 데이터를 기준으로 각각 학습하거나 비교해 고령자 성능을 별도로 확인하려고 합니다.

여기서 받고 싶은 피드백은 다음과 같습니다.

> 이용 가능 연령과 핵심 타깃을 이렇게 분리하는 것이 서비스 기획상 자연스러운지, 아니면 MVP에서는 65세 이상으로 이용자까지 제한해야 메시지와 모델 검증이 더 일관적인지 판단 기준을 듣고 싶습니다.

### 3-2. 당뇨병과 고혈압 구현 순서

기업 요구에는 당뇨병과 고혈압 등이 제시되어 있지만, 현재 모델과 ERD는 당뇨병 3단계 분류가 가장 구체적입니다. 두 질환을 동시에 같은 깊이로 구현하면 범위가 넓어지고, 당뇨병만 구현하면 기업 요구를 좁게 해석했다는 평가를 받을 수 있어 고민하고 있습니다.

팀에서는 **당뇨병 모델을 우선 완성하고, 고혈압은 동일한 API 인터페이스와 공통 데이터 구조로 확장 가능함을 보여주는 방식**을 우선 검토하고 있습니다.

> Sprint 1 이후 MVP에서 당뇨병을 먼저 완성하고 고혈압은 기본 모델 또는 확장 구조로 제시해도 평가 요구에 부합하는지, 아니면 두 질환을 반드시 같은 수준으로 시연해야 하는지 의견을 부탁드립니다.

## 4. AI 모델과 위험도 표현에 대한 피드백 (약 3분)

### 4-1. 다중분류와 목적별 이진분류

당뇨병은 정상, 전당뇨, 당뇨의 3개 클래스로 정의할 수 있습니다. 현재 검토안은 하나의 다중분류 모델을 만드는 방식과, 정상 대 전당뇨, 정상·전당뇨 대 당뇨, 정상 대 당뇨처럼 목적별 이진분류 모델을 만드는 방식입니다.

다중분류는 사용자에게 세 단계를 한 번에 보여주기 쉬운 반면, 경계 집단과 클래스 불균형 때문에 특정 클래스의 재현율이 낮아질 수 있습니다. 목적별 이진분류는 질문별 성능을 최적화하기 쉽지만 여러 모델의 결과가 서로 충돌할 가능성이 있고 서비스 설명도 복잡해집니다.

저희 잠정안은 **다중분류를 주 모델로 두고, 목적별 이진분류를 비교 실험으로 운영**하는 것입니다.

> 서비스 화면은 세 단계 결과를 요구하는 상황에서 다중분류를 주 모델로 두는 것이 타당한지, 아니면 위험군 선별이라는 목적상 이진분류를 우선해야 하는지 궁금합니다. 이때 AUROC보다 전당뇨·당뇨 클래스 Recall, Macro F1, AUPRC와 calibration 중 무엇을 핵심 판단 기준으로 두어야 하는지도 조언받고 싶습니다.

### 4-2. 대시보드 위험도와 변화값

3단계 모델은 정상, 전당뇨, 당뇨 확률을 각각 출력합니다. 그런데 대시보드에서 하나의 위험도와 최초 대비 변화값을 보여주려면 어떤 값을 위험도로 정의할지 결정해야 합니다.

후보는 당뇨 확률만 사용하는 방식, 전당뇨와 당뇨 확률을 합산하는 방식, 클래스별 가중 점수를 만드는 방식, 또는 연속적인 변화율을 보여주지 않고 단계와 확률 분포만 보여주는 방식입니다.

저희는 단순 확률 변화가 실제 건강 개선을 의미한다고 오해될 수 있다는 점도 우려하고 있습니다. 또한 모델 버전이 바뀌면 과거 확률과 최신 확률을 직접 비교하기 어렵습니다.

> 위험군 선별 서비스에서 사용자에게 보여줄 대표 위험값을 무엇으로 정의하는 것이 타당한지, calibration이 확보되지 않은 초기 MVP에서는 변화율보다 단계와 확률 분포만 보여주는 것이 안전한지 피드백을 받고 싶습니다. 변화값을 허용한다면 같은 모델 버전과 동일한 점수 정의 사이에서만 비교하도록 제한하는 것이 맞는지도 확인하고 싶습니다.

## 5. ERD와 비동기 처리에 대한 피드백 (약 2분)

### 5-1. 질환별 클래스 확률 저장 구조

현재 ERD에는 `prob_normal`, `prob_prediabetes`, `prob_diabetes`처럼 당뇨병 전용 컬럼이 있습니다. 고혈압이나 다른 질환으로 확장하면 컬럼을 계속 추가해야 합니다.

검토한 방식은 세 가지입니다. 질환별 컬럼은 단순하지만 확장성이 낮고, JSON 저장은 유연하지만 무결성과 검색이 어렵습니다. 별도 클래스 결과 테이블은 정규화와 확장성에는 유리하지만 MVP 구조가 복잡해집니다.

저희 잠정안은 **예측 기본 정보는 Prediction에 두고, 클래스명과 확률은 별도 PredictionClassResult 테이블에 저장하는 방식**입니다. 필요하면 모델의 원본 응답만 JSON으로 함께 보존하는 안도 검토하고 있습니다.

> 두 질환에서 시작하지만 향후 질환 확장을 전제로 할 때 별도 결과 테이블이 적정한 설계인지, 아니면 교육 프로젝트의 MVP로는 JSON 방식이 더 현실적인지 실무 기준을 듣고 싶습니다.

### 5-2. 비동기 예측 작업 상태

API에는 PredictionJob을 이용한 비동기 예측 흐름이 있지만 ERD에는 아직 작업 엔터티가 없습니다. Redis에 진행 중 상태만 저장할지, DB에도 요청·완료·실패·재시도 이력을 남길지 결정이 필요합니다.

팀의 잠정안은 **Redis는 짧은 작업 상태와 큐 처리에 사용하고, DB에는 작업 ID, 사용자·검진 연결, 모델 버전, 최종 상태, 오류 코드와 주요 시각만 최소한으로 보존**하는 것입니다.

> 작은 규모의 프로젝트에서도 실패와 재시도 이력을 DB에 남기는 것이 추적성과 운영 측면에서 필요한지, 아니면 성공한 Prediction만 DB에 저장해도 충분한지 조언을 부탁드립니다. 과도한 설계를 피하면서도 평가와 시연에 필요한 최소 필드가 무엇인지 알고 싶습니다.

## 6. 의료 안전과 MVP 범위에 대한 피드백 (약 2분)

### 6-1. 기진단 사용자 흐름

현재 요구사항 정의서에는 당뇨병이나 고혈압 기진단자는 예측을 중단하고 의료기관 안내로 이동하도록 되어 있습니다. 반면 와이어프레임에서는 기진단자가 예측만 생략하고 생활습관 챌린지를 이용하는 흐름도 검토하고 있습니다. 두 문서 사이에 아직 정책 차이가 있습니다.

기진단자는 발병 가능성을 예측할 대상은 아니지만, 생활습관 기록 기능 자체는 사용할 수 있습니다. 다만 질환 맞춤 챌린지가 치료나 처방을 대신하는 것처럼 보이면 안전 문제가 생길 수 있습니다.

> 기진단자는 예측에서 제외하되, 담당 의료진의 지침을 우선한다는 안내와 함께 일반적인 생활습관 기록·챌린지만 제공하는 흐름이 적절한지 확인받고 싶습니다. 질환별 맞춤 추천은 제외해야 하는지, 대시보드에는 위험도 대신 생활습관 수행 기록만 보여주는 것이 맞는지도 피드백을 부탁드립니다.

### 6-2. MVP에서 제외할 기능

현재 요구사항에는 LLM·RAG 추천, 의료기관 권고 확인, 알림, 사용자 피드백, 다중 모델 버전, 비동기 처리 등 확장 기능이 포함되어 있습니다.

팀에서는 핵심 흐름을 **동의와 적합성 확인 → 건강정보 입력 → 위험 선별 → 결과 설명 → 챌린지 선택·기록 → 추적 대시보드**로 보고 있습니다. LLM·RAG, 알림, 복잡한 후속 조치와 고도화된 운영 기능은 후순위로 조정하는 안을 검토하고 있습니다.

> 평가 기준에서 AI 모델과 웹서비스 연결을 충분히 보여주면서도 구현 완성도를 확보하려면, 현재 기능 중 반드시 남길 것과 과감히 제외할 것을 구분해 주셨으면 합니다. 특히 비동기 처리와 다질환 확장 구조는 실제 구현까지 필요한지, 설계와 명세로만 보여도 되는지 조언을 부탁드립니다.
