## 1. 2주간 공통 결정

- 이용 가능 연령은 만 19세 이상, 핵심 타깃은 만 40세 이상 당뇨병 미진단자이다.
- Sprint 2 예측 질환은 당뇨병 하나이며 고혈압은 후속 확장 대상으로 둔다.
- 주 예측 문제는 KLoSA의 기준 시점 미진단자가 다음 인접 조사 시점에 신규 진단되는지를 보는 미래 발병 이진분류이다.
- KNHANES는 현재 위험 신호 선별과 변수 정의·단면 베이스라인에 별도로 사용하며 KLoSA와 행 단위로 합치지 않는다.
- 예측 결과는 진단·처방이 아닌 위험 선별·건강교육으로 표현한다.
- 기진단자와 의료진 확인이 우선인 증상 사용자는 예측과 개인화 추천에 진입시키지 않는다.
- 사용자 화면에는 승인된 `낮음·주의·높음` 범주만 표시하고, 검증 전 내부 점수를 개인 발병확률이나 건강 개선율로 표현하지 않는다.
- 예측 작업 API는 `/api/v1/prediction-jobs`, 상태는 `queued/running/succeeded/failed`, 생성 시각은 `created_at`을 기준으로 한다.
- Redis는 단기 작업 상태, DB는 요청·완료·실패·모델 버전과 최소 결과 이력을 담당한다.

## 3. 현재 실행 가능한 범위

### 프로토타입

다음 흐름은 메모리 저장소와 mock 모델로 시연 가능하다.

`가입 → 건강정보 동의 → 적합성 확인 → 건강정보 입력 → mock 예측 → 위험요인 → 챌린지 선택 → 일일 기록 → 대시보드`

### 정식 앱 골격

- 이메일 회원가입·로그인·토큰과 사용자 API
- MySQL/Tortoise ORM 기반 저장 구조
- Redis Stream 작업 큐, Consumer Group, AI Worker, SSE 상태 이벤트
- 로컬 Docker 구성과 실행 스크립트

### 모델

- KLoSA 미래 신규 진단과 KNHANES 현재 위험 신호를 분리한 베이스라인
- Recall 중심 후보 비교·앙상블과 재현 가능한 추론 계약
- Draft PR #4: [KLoSA·KNHANES Recall 중심 모델 및 앙상블](https://github.com/AI-HealthCare-05/AH_05_02/pull/4)

- [ ] 각 팀원이 담당 산출물의 PR 또는 최종 링크를 남기고 최소 1명이 리뷰한다.

## 7. 웹서비스 구현 작업 인수인계

구현 순서는 다음과 같다.

1. 정식 앱을 기준선으로 확정하고 프로토타입의 도메인 기능을 이식한다.
2. `PredictionProvider` 인터페이스를 만들고 기존 개발용 모델을 기본 구현으로 연결한다.
3. 모델 버전·특성 스키마·임계값 버전을 작업과 결과에 저장한다.
4. Draft PR #4가 병합되면 provider 설정만 바꿔 새 모델을 로드한다.
5. 적합성→입력→비동기 작업→범주 결과의 P0 세로 흐름을 먼저 완성한다.
6. 챌린지→일일 기록→대시보드를 정식 DB/API에 연결한다.
7. OT 선택 기능은 P0 완료 후 검토된 템플릿 설명과 출처 표시부터 추가한다. 이미지 식단 분석·알림·생성형 개인 의료 조언은 이번 Sprint에서 제외한다.
