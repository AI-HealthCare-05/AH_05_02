# 2026-08-14 멘토링 요약 브리핑

## 브리핑 목적

Sprint 1 기획 산출물의 진행 상황을 짧게 공유하고, 문서 간 불일치와 MVP 범위를 멘토 피드백으로 확정한다.

---

## 1. 5분 브리핑 대본

안녕하세요. 만성질환 생활습관 챌린지 웹서비스를 기획하고 있는 2조입니다.

저희 서비스는 건강검진과 생활습관 정보를 활용해 당뇨병과 고혈압 위험군을 선별하고, 위험·보호 요인을 설명한 뒤 4주 생활습관 챌린지와 추적 대시보드를 제공하는 서비스입니다. 예측 결과는 진단이나 처방이 아니라 위험 선별과 건강교육 정보로 제공할 예정입니다.

현재 서비스는 만 19세 이상이 이용할 수 있도록 열어두되, 핵심 타깃과 접근성 설계 기준은 만 65세 이상 고령자로 두는 안을 적용하고 있습니다.

Sprint 1에서는 네 가지 기획 산출물의 1차 초안을 완성했습니다.

- 요구사항 정의서는 총 79개로, 기능 요구사항 40개와 비기능 요구사항 39개입니다. 77개는 확정 상태이며, RAG 기반 설명과 의료기관 권고 확인 기능 2개는 후순위로 분류했습니다.
- 와이어프레임은 서비스 소개부터 동의, 적합성 확인, 건강정보 입력, AI 예측, 챌린지, 대시보드까지의 핵심 흐름과 고령자 접근성 기준을 반영했습니다.
- ERD는 15개 핵심 엔터티를 중심으로 건강검진과 예측 이력, 4주 챌린지 사이클, 의료기관 안내와 추천 기록을 설계했습니다.
- API 명세서는 총 44개 엔드포인트를 작성했습니다. 이 중 35개는 명세 완료, 8개는 검토 필요, 1개는 후순위입니다.

데이터는 KNHANES와 KLoSA를 사용합니다. KNHANES는 검진·생활습관 기반 현재 위험 선별에 활용하고, KLoSA는 다음 조사차수의 신규 진단과 종단 변화 분석에 활용합니다. 서로 조사 구조와 대상자가 다르기 때문에 행 단위로 직접 합치지 않고 공통 변수 메타데이터로 연결합니다.

전처리는 KNHANES 2016~2024년 67,019건과 KLoSA 1~10차 74,834개 패널 관측행을 대상으로 진행했고, 중복 키는 없었으며 전처리 테스트 11개가 통과했습니다. 결측 대치와 스케일링은 전체 데이터가 아니라 학습 데이터에서만 적합하도록 설계했습니다.

오늘 네 문서를 다시 대조한 결과, 구현 전에 반드시 맞춰야 할 부분이 확인됐습니다.

첫째, 요구사항 정의서는 기진단 사용자를 예측과 챌린지에서 제외하지만, 와이어프레임에서는 예측만 생략하고 챌린지를 제공하는 흐름도 검토하고 있습니다.

둘째, 화면과 API에서는 혈압·공복혈당·HbA1c를 입력받을 수 있지만, 해당 값은 타깃을 직접 결정할 수 있어 모델 입력에서는 제외해야 합니다. 따라서 수집 데이터와 모델 입력 데이터를 명확히 분리해야 합니다.

셋째, 요구사항은 당뇨병과 고혈압을 모두 필수로 정의했지만 현재 예측 저장 구조는 정상·전당뇨·당뇨 확률처럼 당뇨병 중심입니다. 고혈압과 다른 질환을 확장할 수 있는 공통 구조가 필요합니다.

넷째, 대시보드의 최초 대비 위험도 변화는 같은 모델 버전과 같은 점수 정의 사이에서만 비교해야 합니다. 현재 상태 분류 확률을 실제 건강 개선이나 미래 발병률 변화로 표현해서는 안 됩니다.

다섯째, API에는 비동기 예측 작업이 있지만 ERD에는 PredictionJob 엔터티가 없습니다. 실패·재시도·모델 버전을 어디까지 DB에 남길지 결정해야 합니다.

여섯째, 동의 버전·철회 시각·탈퇴 후 삭제 또는 익명화 정책은 요구사항에는 있으나 ERD와 API에서 아직 완전히 확정되지 않았습니다.

저희 팀의 잠정 권고안은 다음과 같습니다.

- 서비스는 만 19세 이상 이용 가능, 만 65세 이상을 주 타깃으로 유지합니다.
- 당뇨병은 완성도 있는 주 모델로 구현하고, 고혈압은 같은 인터페이스의 베이스라인 모델까지 구현합니다.
- 당뇨병 3단계 다중분류를 주 모델로 두고 목적별 이진분류는 비교 실험으로 사용합니다.
- 기진단자는 위험 예측에서 제외하되 의료진 지침 우선 안내 후 일반적인 생활습관 기록 기능만 제공합니다.
- 위험도 변화는 동일 모델 버전과 동일 점수 정의일 때만 제공하고, 그렇지 않으면 단계와 확률 분포만 표시합니다.
- PredictionJob은 DB에 최소 이력을 남기고, 짧은 작업 상태와 큐 처리는 Redis에서 관리합니다.
- 오늘 RAG 특강 내용은 예방 행동 설명의 근거 제공에 활용하되, Sprint MVP에서는 검토된 템플릿을 우선하고 RAG는 후순위로 유지합니다.

오늘 멘토링에서는 이 잠정안을 기준으로 MVP의 적정 범위와 결정 기준을 확인받고 싶습니다.

## 2. 멘토에게 받을 핵심 피드백

### 질문 1. MVP 질환 구현 범위

당뇨병은 전체 사용자 흐름과 모델을 완성하고, 고혈압은 베이스라인 모델과 확장 가능한 API·DB 구조까지 구현하는 수준이 기업 요구에 충분한가요? 두 질환을 반드시 같은 완성도로 시연해야 하나요?

### 질문 2. 당뇨병 모델 전략

정상·전당뇨·당뇨 다중분류를 주 모델로 하고 세 가지 이진분류를 비교 실험으로 두는 방식이 적절한가요? 평가에서 가장 우선할 지표는 Macro F1, 전당뇨·당뇨 Recall, AUPRC, calibration 중 무엇인가요?

### 질문 3. 위험도 변화 표시

현재 상태 분류 확률을 대시보드의 위험도로 표현해도 되는지, 초기 MVP에서는 위험도 변화 대신 단계와 확률 분포만 제공하는 편이 안전한지 확인하고 싶습니다.

### 질문 4. 기진단 사용자 처리

기진단자는 예측에서 제외하고 의료진 지침 우선 안내 후 일반 생활습관 챌린지만 제공해도 될까요? 질환 맞춤형 추천은 제외하는 것이 적절한가요?

### 질문 5. 비동기 예측과 RAG 구현 수준

PredictionJob의 요청·완료·실패 이력을 DB에 보존하고 Redis를 작업 큐로 사용하는 구조가 MVP에 적절한가요? RAG는 이번 Sprint에서 설계와 안전 기준만 제시하고 후순위로 미뤄도 될까요?

## 5. 마무리 문구

말씀해 주신 내용을 멘토링 직후 확정·수정·후순위로 나누고, 요구사항 정의서·와이어프레임·ERD·API 명세서·AI 실험계획에 같은 기준으로 반영하겠습니다. 가능하다면 각 쟁점에 대해 추천안뿐 아니라 그렇게 판단하는 기준과 MVP에서 필요한 최소 수준도 함께 말씀 부탁드립니다.
