## 실제 진행 내용

### 1. 요구사항 정의서

- 회원·동의·적합성 확인·건강정보·AI 예측·챌린지·대시보드·후속조치 요구사항을 기능/비기능으로 구분했습니다.
- 각 요구사항에 ID, 우선순위, 수용 기준, 상태, 담당자를 지정했습니다.
- 의료·AI 안전, 개인정보보호, 고령자 접근성, 성능, 모델 누수 방지, 비동기 처리와 평가 기준 대응 내용을 포함했습니다.
- 문서: [요구사항 정의서 Drive](https://drive.google.com/drive/u/0/folders/1L0Au1xuZvEzE2GBRU3pWrmEVRjIQobQH)

### 2. 와이어프레임

- 서비스 소개, 동의, 적합성·안전 확인, 검진정보 입력, 예측 결과, 챌린지, 대시보드의 핵심 흐름을 구성했습니다.
- 큰 글자, 명확한 단계 표시, 단일 주요 행동 등 고령자 접근성 방향을 반영하고 있습니다.
- 문서: [Figma 와이어프레임](https://www.figma.com/design/GgsFZ60n8nwxkmIdTRcyHf/%EB%A7%8C%EC%84%B1%EC%A7%88%ED%99%98-%EB%8C%80%EC%8B%9C%EB%B3%B4%EB%93%9C-%EC%98%88%EC%8B%9C?node-id=6-233&t=fzCuEKugrBNk6Cf1-0)

### 3. ERD

- 사용자·동의·적합성·프로필·건강검진·예측·위험요인·4주 챌린지·후속조치·추천·피드백 엔터티를 구성했습니다.
- 건강검진 1건에 여러 모델 버전의 예측을 저장하고, 최초 대비 위험 변화는 조회 시 계산하도록 반영했습니다.
- 4주 단위 `ChallengeCycle`과 날짜별 챌린지 기록의 중복 방지 제약을 반영했습니다.
- 문서: [ERD v2](https://dbdiagram.io/d/erd_v2-6a7c28e3e093539a9e9c43c0)

### 4. API 명세서

- `/api/v1` 기준으로 인증, 동의, 적합성, 건강검진, 비동기 예측, 챌린지, 대시보드, 후속조치, 추천·피드백 API를 정의했습니다.
- 공통 성공·오류 형식, 상태 코드, JWT 권한, 멱등성, 페이지네이션, 모델 실패 처리 기준을 정리했습니다.
- 화면–요구사항–API–DB 추적표와 핵심 요청·응답 예시를 작성했습니다.
- 문서: `docs/API_SPEC.md`

## 현재 막힌 문제

- 대상 연령 표현이 요구사항의 `65세 이상 주 타깃`과 와이어프레임의 `만 19세 이상 이용 가능`으로 나뉘어 있어, 이용 자격과 주 타깃을 분리하는 방식의 확정이 필요합니다.
- 요구사항은 당뇨병·고혈압 2종이나 ERD와 1차 모델안은 당뇨병 3단계 분류 중심이라 MVP 질환 범위와 구현 순서를 확정해야 합니다.
- ERD의 `prob_normal`, `prob_prediabetes`, `prob_diabetes`는 당뇨병 전용 구조여서 고혈압 등 질환 확장 시 클래스 확률 저장 방식을 일반화할지 검토가 필요합니다.
- 비동기 예측 요구사항은 있으나 ERD에는 `prediction_job` 저장 구조가 없어 Redis 작업 상태만 사용할지 DB 이력도 남길지 결정이 필요합니다.
- 생년월일 전체 저장의 필요성과 개인정보 최소수집 원칙, 탈퇴·동의 철회 시 건강정보 보유·삭제 기준을 확정해야 합니다.

## 멘토에게 받고 싶은 피드백

- `만 19세 이상 이용 가능·65세 이상 주 타깃`으로 자격과 타깃을 분리하는 것이 적절한지
- Sprint 1에서 당뇨병을 먼저 구현하고 고혈압을 확장 구조로 남기는 범위가 평가 요구에 부합하는지
- 당뇨병 3단계 분류 결과에서 대시보드용 위험도와 최초 대비 변화값을 어떤 확률로 정의하는 것이 타당한지
- 여러 질환의 단계·클래스별 확률을 저장할 때 질환별 컬럼, JSON, 별도 결과 테이블 중 어떤 구조가 적절한지
- 비동기 추론의 작업 상태를 Redis에만 둘지 DB에도 보존해야 하는지
- 현재 기획 산출물에서 MVP 범위상 우선 제외하거나 추가 보완해야 할 항목이 있는지
