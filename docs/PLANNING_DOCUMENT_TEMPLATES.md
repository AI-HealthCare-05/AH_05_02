# 2. 요구사항 정의서 양식

## 2-1. 작성 단위

- 한 행에는 검수할 수 있는 요구사항 하나만 작성한다.
- 기능 요구사항은 `REQ`, 비기능 요구사항은 `NFR`로 구분한다.
- 상세 설명에는 행위 주체, 조건, 행동, 결과를 포함한다.
- 우선순위와 완료 상태를 반드시 기록한다.

## 2-2. 요구사항 ID 규칙

```text
기능 요구사항: REQ-{CATEGORY}-{번호}
비기능 요구사항: NFR-{CATEGORY}-{번호}
```

### 카테고리 코드

| 코드 | 카테고리 |
|---|---|
| USER | 회원·인증 |
| HEALTH | 건강 프로필·건강기록 |
| PRED | 만성질환 위험 예측 |
| CHAL | 생활습관 챌린지 |
| DASH | 추적 대시보드 |
| RECO | 예방 행동 추천·RAG |
| FEED | 사용자 피드백 |
| PERF | 성능 |
| SEC | 보안·개인정보 |
| SAFE | 의료·AI 안전 |
| OPS | 배포·운영·모니터링 |

예시: `REQ-PRED-001`, `NFR-SEC-001`

## 2-3. 최종 열 구성

| 요구사항 ID | Category | Depth1 | Depth2 | Depth3 | 요구사항 상세 설명 | 기능/비기능 | 우선순위 | 비고 | 상태 | 담당자 |
|---|---|---|---|---|---|---|---|---|---|---|
| REQ-PRED-001 | 예측 | 위험 예측 | 건강 설문 | 결과 제공 | 인증된 사용자는 필수 건강정보를 입력하고 만성질환 위험 선별 결과를 조회할 수 있어야 한다. | 기능 | 높음 | 필수 입력값 누락 시 400 반환 | 대기중 | 양준혁·박빛샘 |

## 2-4. 입력 규칙

| 항목 | 입력 규칙 |
|---|---|
| 요구사항 ID | 중복 없이 ID 규칙에 따라 작성 |
| Category | 회원·건강·예측·챌린지·대시보드 등 업무 영역 |
| Depth1 | 사용자 관점의 상위 기능 |
| Depth2 | 하위 기능 또는 화면·처리 단계 |
| Depth3 | 세부 행동 또는 예외 상황 |
| 요구사항 상세 설명 | 누가, 어떤 조건에서, 무엇을 하고, 어떤 결과를 얻는지 작성 |
| 기능/비기능 | `기능` 또는 `비기능` |
| 우선순위 | `높음`, `보통`, `낮음` |
| 비고 | 제약사항·예외·검수 기준·관련 문서 |
| 상태 | `대기중`, `진행중`, `완료`, `보류` |
| 담당자 | 구현 책임자 이름 |

## 2-5. 비기능 요구사항 필수 범위

- 성능: 주요 API P95 응답시간 등 측정 가능한 수치
- 보안: 인증·인가, 비밀번호 해시, 민감정보 최소수집
- 접근성: 입력 라벨, 키보드 이용, 색상 외 상태 표시
- 안정성: 동일 입력·동일 모델 버전의 일관된 결과
- 유지보수성: 모듈 분리, 코드 품질, 문서 동기화
- 로그·모니터링: 주요 오류와 추론 이력 기록
- 의료 안전: 진단·처방 표현 제한, 응급·의료기관 안내

권장 도구: DB Diagram, ERDCloud, draw.io

## 3-2. 엔터티 목록

| 엔터티명 | 한글명 | 역할 | 주요 데이터 | 개인정보 여부 | 담당자 |
|---|---|---|---|---|---|
| users | 사용자 | 계정과 인증정보 저장 | 이메일, 비밀번호 해시 | 예 | 박빛샘 |

## 3-3. 엔터티별 컬럼 정의

### 엔터티: `{table_name}`

| 컬럼명 | 한글명 | 데이터 타입 | PK | FK | NULL 허용 | 기본값 | 설명 |
|---|---|---|---|---|---|---|---|
| id | 식별자 | BIGINT | Y | N | N |  | 내부 식별자 |
| created_at | 생성일시 | TIMESTAMP | N | N | N | CURRENT_TIMESTAMP | 레코드 생성일시 |
| updated_at | 수정일시 | TIMESTAMP | N | N | N | CURRENT_TIMESTAMP | 최종 수정일시 |

## 3-4. 관계 정의

| From 엔터티 | To 엔터티 | 관계 | 외래키 | 삭제 정책 | 설명 |
|---|---|---|---|---|---|
| users | predictions | 1:N | predictions.user_id | RESTRICT 또는 CASCADE 확정 필요 | 한 사용자는 여러 예측 이력을 가진다. |

## 3-5. 필수 검토사항

- 모든 엔터티에 기본키가 존재하는가?
- 외래키와 관계 방향이 표시되어 있는가?
- N:M 관계를 연결 엔터티로 해소했는가?
- 생성일·수정일과 모델 버전 등 이력 필드가 있는가?
- 건강정보와 개인정보를 필요한 범위에서만 저장하는가?
- 화면 입력값, 모델 입력값, API 필드와 명칭이 일치하는가?

# 4. API 명세서 양식

## 4-1. 문서 상단 공통정보

| 항목 | 작성 내용 |
|---|---|
| API Domain | 개발·운영 서버의 기본 도메인 |
| API Version | `v1` |
| Content-Type | `application/json` |
| 인증 방식 | JWT Bearer 등 팀 결정 |
| 공통 오류 | 401, 403, 404, 422, 500 등 공통 응답 |
| 네이밍 규칙 | URL은 복수 명사·kebab-case, JSON은 snake_case 등 팀 규칙 |

## 4-2. 최종 열 구성

| Version | Request URL | HTTP Method | Short Description | Header Schema | Header Example | Query Parameter Schema | Query Parameter Example | Request Body Schema | Request Body Example | Success Response Schema | Success Response Example | Error Response Schema | Error Response Example | Status Code | 담당자 | 완료 상태 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| V1 | `/api/v1/predictions` | POST | 만성질환 위험 예측 | Bearer token | `Authorization: Bearer ...` |  |  | 별도 스키마 작성 | 별도 예시 작성 | 별도 스키마 작성 | 별도 예시 작성 | 400·401·422·500 | 오류별 예시 작성 | 200, 400, 401, 422, 500 | 박빛샘·양준혁 | 대기중 |

## 4-3. Schema 작성 형식

```text
{
  "field_name": {
    "type": "string | integer | number | boolean | array | object",
    "required": true,
    "description": "필드 설명"
  }
}
```

## 4-4. 필수 상태 코드

| 코드 | 의미 | 사용 예 |
|---|---|---|
| 200 | 조회·수정 성공 | 결과 조회, 수정 |
| 201 | 생성 성공 | 회원가입, 기록 생성 |
| 204 | 본문 없는 성공 | 삭제 성공 |
| 400 | 잘못된 요청 | 형식 오류·필수값 누락 |
| 401 | 인증 필요 | 토큰 누락·만료 |
| 403 | 접근 권한 없음 | 다른 사용자의 건강기록 접근 |
| 404 | 리소스 없음 | 예측·챌린지 기록 없음 |
| 409 | 데이터 충돌 | 이메일 중복·중복 참여 |
| 422 | 검증 실패 | Pydantic 입력 검증 실패 |
| 500 | 서버 오류 | 처리되지 않은 내부 오류 |

## 4-5. 작성 규칙

- 모든 Request·Response에 Schema와 Example을 함께 작성한다.
- 인증이 필요한 API는 Header에 명시한다.
- 오류마다 상태 코드, 오류 필드, 메시지 예시를 작성한다.
- 구현 후 FastAPI Swagger UI와 시트 내용을 일치시킨다.
- 모델 API에는 모델 버전, 예측 시점, 결과 의미를 포함한다.

# 6. 문서 간 연결 규칙

| 요구사항 정의서 | ERD | API 명세서 | 와이어프레임 |
|---|---|---|---|
| 요구사항 ID | 저장 필드 | 요청·응답 필드 | 화면 기능·관련 요구사항 |
| 기능 우선순위 | 엔터티 구현 범위 | API 구현 순서 | 화면 제작 순서 |
| 예외 상황 | 제약조건 | 오류 상태 코드 | 오류·빈 상태 화면 |
| 행위 주체 | 사용자 소유 관계 | 인증·인가 | 사용자별 접근 화면 |

모든 핵심 기능은 다음 연결을 가져야 한다.

```text
요구사항 ID → 화면 ID → API Endpoint → DB 엔터티·필드
```

AI 예측 기능은 다음 연결을 추가로 기록한다.

```text
화면 입력 → API 요청 → 모델 입력 변수 → 모델 출력
→ API 응답 → 예측 이력 저장 → 결과 화면
```
