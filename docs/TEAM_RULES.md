# 팀 룰

버전: `v0.1`

## 1. 기본 원칙

1. 개인의 작업량보다 팀 전체의 완성을 우선한다.
2. 진행 상황과 문제를 숨기지 않고 빠르게 공유한다.
3. 중요한 결정은 메신저에만 남기지 않고 GitHub 또는 문서에 기록한다.
4. 상대방의 코드와 의견을 비난하지 않고 개선점을 구체적으로 제안한다.
5. 담당자가 있더라도 기능 완성에 대한 책임은 팀 전체가 공유한다.
6. 의료 서비스의 안전성과 개인정보 보호를 개발 편의보다 우선한다.

## 2. 역할과 책임

| 역할 | 주요 책임 |
| --- | --- |
| PM·기획·문서·QA | 일정, 요구사항, 회의, 문서, 발표, 통합 테스트 |
| AI·데이터·RAG | 데이터, 예측 모델, 모델 평가, SHAP, RAG, sLLM |
| 백엔드·DB·인프라 | FastAPI, 인증, DB, 모델 연동, Docker, EC2 |
| 프론트엔드·UI/UX | 화면, 대시보드, 챌린지, 시각화, API 연동 |

- 각 담당자는 작업 시작 전에 완료 기준을 확인한다.
- 다른 영역에 영향을 주는 변경은 관련 담당자와 먼저 협의한다.
- 작업이 어려워지거나 지연될 가능성이 생기면 즉시 공유한다.
- 역할 경계를 이유로 필요한 지원을 거절하지 않는다.

## 3. 회의 방식

### 데일리 스탠드업

- 매일 10분 이내로 진행한다.
- 어제 한 일, 오늘 할 일, 막힌 문제를 공유한다.
- 긴 토론은 종료 후 관련자끼리 진행한다.

### 주간 계획회의

- 매주 월요일에 이번 주 목표와 우선순위를 정한다.
- 작업을 GitHub Issue로 만들고 담당자와 마감일을 지정한다.

### 기술 연동회의

- 매주 수요일 또는 필요할 때 진행한다.
- 모델 입출력, API, DB, 화면 연동을 점검한다.
- 변경된 명세는 회의 직후 문서에 반영한다.

### 주간 데모·회고

- 매주 금요일에 실제 화면으로 구현 결과를 시연한다.
- 잘된 점, 문제점, 다음 개선 사항을 기록한다.
- README와 발표자료를 함께 업데이트한다.

## 4. 소통 규칙

- 일반 질문은 팀 공용 채널에서 공유한다.
- 개인 메시지에서 결정된 내용은 공용 채널이나 문서에 다시 남긴다.
- 긴급한 문제는 담당자를 멘션한다.
- 바로 처리하기 어렵다면 확인 여부와 예상 처리 시간을 답한다.
- 의견에 반대할 때는 이유와 가능한 대안을 함께 제시한다.

## 5. 작업 관리

모든 개발 작업은 다음 순서로 진행한다.

```text
요구사항 확인 → Issue 생성 → 담당자 배정 → 브랜치 생성
→ 개발·테스트 → Pull Request → 리뷰·CI → 병합
```

Issue에는 목적, 작업 내용, 완료 조건, 관련 기능, 예상 마감일을 작성한다.

## 6. Git 규칙

### 브랜치

- `main`: 배포 가능한 안정 버전
- `develop`: 개발 기능 통합
- `feature/*`: 새로운 기능
- `fix/*`: 일반 버그 수정
- `release/*`: 배포 준비
- `hotfix/*`: 운영 긴급 수정
- `docs/*`: 문서 변경

예시:

```text
feature/18-ml-disease-prediction
feature/21-be-challenge-api
feature/27-fe-health-dashboard
docs/31-api-specification
```

### 보호 규칙

- `main`, `develop`에 직접 Push하지 않는다.
- 모든 변경은 Pull Request로 병합한다.
- Force Push를 금지한다.
- 비밀정보, 개인정보, 원본 의료 데이터를 커밋하지 않는다.
- 기능 브랜치는 병합 후 삭제한다.

### 커밋 메시지

```text
feat: 새로운 기능
fix: 버그 수정
docs: 문서 변경
test: 테스트 추가
refactor: 코드 구조 개선
data: 데이터 처리
model: AI 모델 변경
chore: 설정 및 기타 작업
```

## 7. Pull Request와 코드 리뷰

- PR에는 변경 내용, 이유, 테스트 방법, 관련 Issue를 작성한다.
- 최소 1명의 승인을 받은 후 병합한다.
- 작성자는 자신의 PR을 승인하지 않는다.
- CI 실패 상태에서는 병합하지 않는다.
- 큰 기능은 가능한 한 작은 PR로 나눈다.
- 리뷰 의견은 `필수 수정`, `제안`, `질문`으로 구분한다.
- 리뷰 요청은 가능한 한 당일 확인한다.

## 8. 의사결정 방식

- 담당 영역의 일반 결정은 해당 담당자가 내린다.
- 다른 영역에 영향을 주는 결정은 관련 담당자와 협의한다.
- 기능 범위, 데이터, 기술 스택, 배포 구조는 전체회의에서 결정한다.
- 전체 합의를 우선하고 어려우면 4명 중 3명 이상의 동의로 결정한다.
- 2대 2인 경우 제품·일정은 PM, 기술 구현은 해당 기술 담당자가 결정한다.
- 중요한 기술 결정은 `docs/decisions/`에 이유와 대안을 기록한다.

## 9. 일정과 지연 관리

- 지연 가능성이 생기면 원인, 현재 상태, 필요한 지원, 새 일정을 공유한다.
- 한 사람이 하루 이상 막혀 있으면 페어 작업 또는 담당 조정을 검토한다.
- 필수 기능을 선택 기능보다 우선한다.
- 마감 직전에는 신규 기능보다 오류 수정과 배포 안정화를 우선한다.

우선순위는 다음과 같다.

1. 만성질환 예측 모델
2. 건강 추적 대시보드
3. 생활습관 챌린지
4. 배포와 통합 테스트
5. RAG 예방 행동 추천
6. 식단 이미지 분석
7. 알림과 sLLM·vLLM 고도화

## 10. 완료 기준

다음 조건을 모두 충족해야 완료로 인정한다.

- 요구사항이 구현되고 로컬에서 정상 동작한다.
- 관련 테스트와 CI가 통과한다.
- 예외 상황을 처리한다.
- 필요한 문서가 업데이트됐다.
- 리뷰가 완료됐다.
- 다른 기능을 손상시키지 않는다.
- 비밀정보와 개인정보가 포함되지 않았다.

## 11. 의료·AI 안전 규칙

- 서비스 결과를 의료 진단으로 표현하지 않는다.
- 약물의 복용 시작·중단·변경을 추천하지 않는다.
- 고위험 결과에는 의료기관 상담 안내를 표시한다.
- RAG는 질병관리청·보건복지부 등 검증된 자료를 우선 사용한다.
- AI 답변에는 참고 출처와 한계 문구를 표시한다.
- 모델은 재현율, AUROC, 오류 사례와 성별·연령별 편차까지 점검한다.
- 실제 주민등록번호, 연락처, 진료기록을 테스트 데이터로 사용하지 않는다.

## 12. 보안 규칙

- API 키는 `.env`와 GitHub Secrets로 관리한다.
- `.env`를 커밋하지 않고 `.env.example`만 제공한다.
- 사용자 비밀번호는 안전한 해시로 저장한다.
- 로그에 건강정보, 토큰, 비밀번호를 기록하지 않는다.
- 외부 API로 전달하는 데이터는 최소화한다.

## 13. 갈등 해결

1. 사람과 문제를 분리한다.
2. 각자 근거와 대안을 설명한다.
3. 목표와 일정에 가장 적합한 안을 선택한다.
4. 해결되지 않으면 PM이 중재한다.
5. 기술적 위험이 크면 담당 멘토에게 근거와 함께 문의한다.
6. 결정 후에는 팀 결정에 따른다.
